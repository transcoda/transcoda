# Integrations gate: subtitles, deep health, Bazarr and Seerr

The manual run on a real server that closes the integrations work: the API facts the Bazarr and Seerr plugins were written against (from memory of those projects, not checked against a running server), a real subtitle job end to end, and the deep health check from a monitor. The plugins' tests use hand-written fictional fixtures, so this run is the first time either plugin talks to the real thing. User-facing docs: [`plugins.md`](plugins.md) (Bazarr, Seerr, "Subtitles from Bazarr into the file") and [`env.md`](env.md#monitoring) (deep health).

Fill in the **Outcome** column. A fact that turns out wrong is a finding: note what the server answered, and whether the coded fallback covered it.

## Setup

- Transcoda from branch `integrations`, with the `bazarr` and `seerr` plugins from the plugins repo's `bazarr-seerr` branch installed and configured (URL, API key; path mappings empty when Bazarr sees `/data/shows` and `/data/movies` like Sonarr does).
- **Test connection** on both cards before anything else (it exercises B1, B2, B8, S1 and S2).
- For the requests below, put the keys in the shell, not in this file: `export BAZARR_KEY=…` and `export SEERR_KEY=…`. Replace `bazarr:6767` and `jellyseerr:5055` with your addresses and the example ids with real ones from your library.

## Bazarr API facts (B1–B8)

| # | Fact | Coded fallback | How to check | Outcome |
| --- | --- | --- | --- | --- |
| B1 | The API key goes in the header `X-API-KEY`. | None needed: a 401 or 403 is reported as `Bazarr rejected the API key`. | `curl -s -o /dev/null -w '%{http_code}\n' -H "X-API-KEY: $BAZARR_KEY" http://bazarr:6767/api/system/status` gives `200`; without the header `401`. || Confirmed 2026-10-18 (Bazarr 1.6.2): wrong or missing key → 401. |
| B2 | `GET /api/system/status` answers `{ data: { bazarr_version: "v1.x.y", … } }`. | The version is read from `data.bazarr_version` or `data.version`, a leading `v` dropped; no version means `the address answered, but it is not Bazarr`. | The B1 request with the body printed: `data.bazarr_version` is there. **Test connection** shows `Bazarr <version> at <origin>`. || Confirmed (1.6.2). |
| B3 | `GET /api/series?start=0&length=-1` lists every series as `{ data: [{ sonarrSeriesId, title, path }], total }`; `GET /api/movies?start=0&length=-1` lists every movie with `radarrId`, `title` and `path` (the movie file). | When `length=-1` is ignored (`total` larger than `data`), the plugin pages with `start=<n>&length=500`. A series without `path` is matched by title against the file's three nearest folder names (year in brackets dropped); exactly one hit or unknown. | Both requests: `data` has as many rows as `total`, each series row has `path` (the series folder), each movie row the file path. || Confirmed: series `path` is the folder without a trailing slash; movie `path` is the file. |
| B4 | `GET /api/episodes?seriesid[]=<id>` (and `?episodeid[]=<id>`) answers `{ data: [{ sonarrSeriesId, sonarrEpisodeId, path, subtitles: [{ code2, code3, path, forced, hi }] }] }`; movies `GET /api/movies?radarrid[]=<id>`. A subtitle with `path: null` is a track inside the video. | `code3` missing → `code2`; `forced` and `hi` accept booleans or `"True"`/`"False"`. | `curl -s -g -H "X-API-KEY: $BAZARR_KEY" 'http://bazarr:6767/api/episodes?seriesid[]=12'` for a series with an external and an embedded subtitle: both appear, the embedded one with `path: null`. **Subtitles in Bazarr** on that file lists the same languages. || Differs: embedded tracks are listed only for languages in the item's language profile (none without a profile); `path: null` for embedded. Wording fixed in 627511c. |
| B5 | `PATCH /api/episodes/subtitles?seriesid=<id>&episodeid=<id>&language=<2-letter>&forced=False&hi=False` (movies `PATCH /api/movies/subtitles?radarrid=<id>&…`) searches the providers and downloads synchronously; answers `204`. | Whatever the PATCH answers (an error status or a timeout included), the plugin polls the item every 3 s until the deadline; the result is what Bazarr lists. | Run it with `curl -s -X PATCH -o /dev/null -w '%{http_code} %{time_total}\n'` for an episode missing a language: the status, how long it took, and whether the file is next to the video when it returns. || Differs: the PATCH is queued (204 at once, even for an unknown id); the search runs later. Polling covers it; comments fixed in 627511c. |
| B6 | `PATCH /api/series?seriesid=<id>&action=scan-disk` (movies `PATCH /api/movies?radarrid=<id>&action=scan-disk`) rescans that item's subtitles on disk. | A 4xx gives `Bazarr refused the rescan (<status>)`; the step is optional, so the job stays done with a warning. | Delete nothing; copy a subtitle file next to an episode by hand, send the PATCH, then the B4 request: the new subtitle is listed. || Confirmed: `scan-disk`, 204, synchronous; an unknown action is 400. |
| B7 | Bazarr learns a changed file path from Sonarr or Radarr (its sync), not from `scan-disk`. | **Rescan in Bazarr** looks the item up under the new path, then the old one; a stale path is reported, never fixed. | In the end-to-end mp4 run below (container change): the Bazarr rescan message right after the job, and the B4 path a few minutes later. || Confirmed. |
| B8 | This API exists from Bazarr 1.4.0 on. | Below 1.4.0 **Test connection** says `too-old`. | Record the version above. || Confirmed (1.6.2). |

## Seerr API facts (S1–S6)

| # | Fact | Coded fallback | How to check | Outcome |
| --- | --- | --- | --- | --- |
| S1 | The API key goes in the header `X-Api-Key` and acts as the admin user. | A 401 or 403 is `Seerr rejected the API key`. | `curl -s -o /dev/null -w '%{http_code}\n' -H "X-Api-Key: $SEERR_KEY" http://jellyseerr:5055/api/v1/auth/me` gives `200`; without the header `401` or `403`. || Confirmed live (Seerr 3.5.0): the key acts as user 1; wrong key 403, no key 401. Every keyed call is 403 until a user exists. |
| S2 | `GET /api/v1/status` answers `{ version, … }` without a key; `GET /api/v1/auth/me` with the key alone (no session cookie) answers the user. | No string `version` (or a non-2xx below 500) means `the address answered, but it is not Jellyseerr or Overseerr`; a 5xx is reported as is. | `curl -s http://jellyseerr:5055/api/v1/status` shows `version`; the S1 request answers 200. || Confirmed live: `/status` needs no key; `/auth/me` with the key alone answers the admin. |
| S3 | `GET /api/v1/movie/<tmdbId>` and `GET /api/v1/tv/<tmdbId>` carry `mediaInfo.requests: [{ id, status, createdAt, requestedBy: { id, displayName } }]`; status `3` is declined (`4`, failed, still counts as requested). | No `mediaInfo` → not requested; no or bad `createdAt` → `requestedAt` `unknown`; 404 → unknown. | The movie request for a title someone requested, and one for a title nobody requested: the first has `mediaInfo.requests`, the second none. **Request (Seerr)** with Radarr's ids gives the same answer. || Differs, confirmed live: an unknown TMDB id answers 500 (now read as unknown, 627511c); `requestedBy` has no email; a known unrequested item has `requests: []`, a never-seen one no `mediaInfo`. |
| S4 | `GET /api/v1/search?query=<title>&page=1` answers `{ results: [{ id, mediaType, title or name, releaseDate or firstAirDate, mediaInfo? }] }` (`mediaType` `movie`, `tv` or `person`); some punctuation in `query` makes it answer 400. | On 400 one retry with the title reduced to letters, digits and spaces; still failing, or not exactly one match → unknown. | Search a plain title, then one with a colon or an apostrophe: note which answer 400. **Request (Seerr)** with only a title connected finds the plain one. || Differs: raw `' ( ) ! *` in the query gets 400; strict encoding in 627511c, re-checked live (200 with results). Search hits carry no `requests`, so the by-id lookup follows. |
| S5 | There is no TVDB lookup; Sonarr's ids usually carry a TMDB id. | A TVDB id alone needs a title (searched as a show); without one the answer is `Seerr cannot look up a TVDB id; connect a title`. | **Original language (Sonarr)** → **Request (Seerr)** on three series: the `ids` output has a `tmdbId` on each. || Confirmed. |
| S6 | `displayName` can be an email address (a local user without a user name). | A display name containing `@` is shown as `user #<id>`. | `/api/v1/user` (as admin): any user whose `displayName` is an address. If there is one, a title they requested shows `user #<id>` in the job trace. || Confirmed live: a local user without a user name shows its email as `displayName`, shown as `user #<id>`. |
