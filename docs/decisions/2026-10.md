## 2026-10-18 Integrations (Bazarr, Seerr, sidecar subtitles, deep health)

Built on `integrations`: extra input files in the build model, the embed-sidecar and recycle steps, the deep health check, and the Bazarr and Seerr plugins. Gate outcomes are in `integrations-gate.md`.

### Extra input files and sidecars

- **`ExtraInput.codec` is required:** `fitToContainer` rewrites a stream's codec to `mov_text`, so the original is kept on the input. The diff (`convert subrip→mov_text`) and the "container can't hold it" check need it. `renderArgs` adds `-f <demuxer>` before each extra `-i` (subrip `srt`, ass/ssa `ass`, `webvtt`, `hdmv_pgs_subtitle` `sup`); any other codec is a `RenderError`.
- **The walker guard fails closed:** it applies to anything that is not a core node, including a missing registry entry. It compares `JSON.stringify` of `extraInputs` and the extra-stream pairs `(sourceIndex, input)` sorted by `sourceIndex`; source streams only must keep `input` 0. A plugin may edit an extra stream's flags but never add, remove or re-point an input. Why: a plugin must not be able to make ffmpeg read an arbitrary path.
- **Sidecars are copied before ffmpeg sees them:** `FsOps.copyRegular` opens with `O_NOFOLLOW`, checks the handle (regular file, at most 8 MiB, recounted while streaming) and writes `<tempDir>/sidecar-<n><ext>` exclusively with mode 0600. The original path never reaches ffmpeg. Why: no symlink or swap between check and use (TOCTOU). The 8 MiB cap lives only in `engine/paths.ts`; discovery skips larger files for every format.
- **Discovery is just as strict:** the head read opens with `O_NONBLOCK` and refuses anything that is not a regular file (a FIFO would block). The video's own base name is always a candidate owner. `ExtraInput.path` is the realpath.
- **Embed reason format:** `embed A (deu, forced), B (eng)`, each skip appended as `; skipped <file>: <reason>`. Nothing embedded but something skipped starts `no subtitle file embedded`; no candidates reads `no subtitle files next to the video`. `already has <lang>[ forced][ sdh]` uses the 639-2/T code; an untagged file reads `language und not selected`.
- **Nothing embedded returns the incoming model unchanged** (no `extraInputs: []` key), so a re-run is `nothing_to_do`.
- **Order and defaults:** embedded streams go after the highest existing `order` (kept or dropped), in sidecar name order; a `default` token sets the flag and `normalizeDefaults` keeps the first default per type. The same language twice (`en.eng`) is one language, not a skip. A later embed node counts kept extra streams as existing and skips a path that is already an input, whatever `skipExisting` says.
- **Names, not indexes:** an extra stream is named by file name (`subtitle Show.fr.sup`) in core node reasons and target warnings, never `#-1`. Source streams keep `#n`.
- **Dropped sidecar:** diff line `drop subtitle from <file> (container can't hold it)`, so the plan note is exactly `container can't hold it`. Plan table "Subtitle files", header `N of M embedded`. The verify check counts kept extra streams whose output position holds a subtitle of the same language; a missing sidecar also fails stream-count.
- **Recycle after the replace:** sidecars go to the recycle folder right after the replace installs, before later finish actions (the recovered-replace path too), with `renameNoClobber`. The path must be inside the library root and equal its realpath (the same check as the copy), else a problem and the file stays. A sidecar is recorded before the folder sync; a failed sync is a problem, not a failed recycle. Problem text uses the error code, so no full path appears in a job reason. If the unlink after the link fails the file stays under both names; that is reported and not recorded.
- **mp4 output always has a default video:** when none is flagged, the first kept non-cover video is, with the plan note `mp4 cannot have no default video`. Why: the mp4 muxer flags it anyway, so verify failed on `default, expected not default` after a remux from an mkv without one. mkv is unchanged.

### Deep health check

- **`GET /system/health?deep=1` (or `deep=true`):** any other value is a 400. Failure is a 503 with the failing checks named; the result is cached 10 s, stamped when the check finished. A check that throws unexpectedly is not cached.
- **Checks:** ffmpeg available, scratch space against `MIN_FREE_GIB` (plain decimals, no sign or exponent), and no stalled job (`STALL_HOURS`; `deciding` counts as running). Paused work is ignored: a paused queue is ok. Each check is raced against 5 s, so a hung statfs is a failure, not a hung monitor.
- **Logging:** a failed check logs a warning; a thrown one adds `error`. The message may carry a path, so it goes to the server log only, never the response.

### Bazarr plugin

- **`get-subtitles-now` waits at most 25 s (default 25), not the design's 120 s:** a plugin call is limited to 30 s (`plugins.limits.callTimeoutMs`), and the lookups and the last check count against the wait. `waitSeconds` has `.max(25)` and build clamps again. The reason names the clamped value. Each request gets the remaining budget (at least 1 s), so the last request may end about 1 s past the budget, inside the 30 s.
- **Polling:** the PATCHes run together (`Promise.allSettled`); a PATCH that times out is ignored, any other fetch failure ends with `Bazarr unreachable: <kind>; continuing without new subtitles`, and HTTP errors on the PATCH are ignored since the listing is the truth. One reload right after the PATCHes, then polls at 0, 3 and 6 s steps; the last poll is at the deadline, never after. A dry run makes no calls at all.
- **B5 (differs from the assumption): the subtitle PATCH is queued, not synchronous.** Bazarr answers 204 at once, even for an unknown id, and the result shows up in a later listing. Why polling stays: it was already right; only comments and a test name said "synchronous".
- **B4 (differs): embedded tracks are listed only for languages in the item's Bazarr language profile** (default `embedded_subs_show_desired`), and not at all for an item without a profile. The API cannot reveal the rest. Setting and node descriptions now say so (`EMBEDDED_CAVEAT`); an item with no profile gives no languages, not an error.
- **Lookup:** movies cache only `{id,title,path}` (10 min); the subtitle list is always read fresh by `radarrid[]` after the path match. Episodes are fetched per series, uncached. The title fallback is only for series entries without a `path`. Movie `title` has no year (B3). Episode item title is `<series> S01E03`.
- **Languages:** `subtitles-present` compares through `lang.toIso3` (`ger` equals `deu`). An unknown-language subtitle stays `unknown` and is left out of the summary. The `test()` status call has a 10 s timeout.
- **Version check:** numeric, 1.4.0 or newer; an unparsable version is `wrong-product`; `data.bazarr_version` (no leading `v`), else `data.version`. `rescan`: 4xx is `ok: false`, 5xx adds `retryable: true`; an item gone after the scan says so.
- **Secrets:** the key travels only in `auth` (`X-API-KEY`); a sentinel test covers every hook on the happy and failing paths, movies included.

### Seerr plugin

- **S4 (differs): the 400 was the plugin's own doing.** Seerr rejects an unescaped `' ( ) ! *` in `query` ("must be url encoded"), and `encodeURIComponent` leaves those alone. `strictEncode` escapes them (`%27 %28 %29 %21 %2A`) for every query value. The cleaned-title retry stays as a safety net, only when the cleaned title differs.
- **S3 (differs): an unknown TMDB id answers 500, not 404** ("Unable to retrieve movie."). The plugin maps a 500 from `/movie/` or `/tv/` to unknown with `Seerr could not load TMDB id N (unknown id, or TMDB unreachable)`. A known but never requested title has `mediaInfo.requests: []` and reads as not requested. `requestedBy` carries no `email` (Seerr filters it).
- **Search hits carry no `requests`:** the matched hit's own list is used only when non-empty; otherwise the lookup goes by id (S3), so an empty list is re-verified.
- **Ids:** tmdb and tvdb together mean tv; tmdb only means a movie guess, checked against a connected title when there is one; tvdb only searches by title (kind tv) or, without a title, is unknown (`Seerr cannot look up a TVDB id; connect a title`). Title-only matches without a year say `(matched by title, no year)`.
- **Requests:** declined (status 3) is ignored; failed (4) still counts as requested; earliest by `createdAt`, a missing one sorts last, an invalid one reads `unknown` (`date unknown`).
- **Privacy:** a `displayName` containing `@` (Seerr falls back to the email) is shown as `user #<id>`, or `unknown`; an address is never output.
- **Statuses:** 401/403 `Seerr rejected the API key`; 404 `Seerr does not know TMDB id N`; others `Seerr answered HTTP n for ...`. A 5xx on `/status` is `other`. No `instanceof`; fetch failures go through `fetchErrorKind`, HTTP statuses are data.
- **Notify-requester is dropped**; Task 5's docs say so.

### Plugin conventions and gate

- **Shared helpers:** Bazarr and Seerr use `@transcoda/plugin-arr-common` (a workspace devDependency inlined in the bundle), like Sonarr and Radarr. Query keys are written literally (`seriesid[]=1`), values percent-encoded.
- **Gate run (2026-10-18, real Sonarr 4.0.20, Radarr, Bazarr 1.6.2 and Seerr 3.5.0):** 10 of 14 assumptions confirmed as written; B4, B5, S3 and S4 differ and are all fixed (above). Seerr was finished against a live instance with a temporary Jellyfin. Not tested: B5 with a real subtitle provider (none configured).

### Size gate: webhook body

- **A kept original is visible in the webhook body.** `core:notify-webhook` wired to the size gate's No output sends `outcome: "kept_original"` plus `reason` (for example `saved only 3.2%, below 10%`), with `replacedTo: null` and `afterBytes` the size of the discarded result. On every other path `outcome` is `"done"` and there is no `reason` key. The other fields are unchanged (`jobId`, `runId`, `path`, `workflowId`, `workflowVersion`, `beforeBytes`, `afterBytes`, `replacedTo`). Why: the job ends `kept_original`, so a receiver should not read a kept file as a success.

## 2026-10-19 Several finish steps on one output (gate finding C1)

- **The bug:** the walk refused any file output with more than one edge, so `examples/workflows/track-cleanup-plugins.json` (Sonarr rescan, Jellyfin refresh and ntfy all off Replace original) failed every job at run time (`replace: output file has 3 connections; a file follows one`) although validation accepted it and `plugins.md` promised it. Plugin finish nodes have no outputs, so they could not be chained instead.
- **Decision (option (a) of the finding):** a file output may feed several nodes when **every** node it feeds is a finish node. The walk collects every finish node reachable from that output (each followed by the output a file leaves it by: the size gate's `pass`, a bypassed node's first) and runs them as if they were chained in phase order: a node runs after the finish nodes wired before it; among the nodes free to run, the lower phase (`gate → write → library-manager → media-server → notify`) goes first, then the node further left on the canvas (`position.x`), then the higher one (`position.y`), then the node earlier in `graph.nodes` (last resort, for nodes on the same spot). Canvas position was chosen (the owner, via the controller) because people can see it; the order nodes were added cannot be seen. A finish node without a phase (none in core or plugins) runs last. The path ends with them. Everything downstream is unchanged because it only sees the order: the actions list is in phase order, so the write runs before the plugin steps, `problemsSoFar` carries earlier problems into later steps, `afterReplace` runs right after the write, and the pipeline's phase checks never fire.
- **Size gate:** a gate among the shared finish nodes still has its `else` walked apart. The `else` output may itself feed several finish nodes (the same ordering; anything else fails the walk with `only finish steps can follow the size gate's No branch`, and a writing step there still fails the build); `pass` may too.
- **Refusals:** an output shared with any non-finish node fails the walk at the node it leaves (`output <port> has <n> connections; only finish steps can share an output`); a non-finish node behind one of the shared finish nodes fails at that node (`<node> comes after a finish node; only finish nodes may follow one`, as `FINISH_ORDER` says at save).
- **Validation `OUTPUT_MULTIPLE_EDGES` (error, on the node whose output is shared):** `<node>: output <label> has <n> connections; only finish steps can share an output (a file follows one path)`, for a file output with two or more edges where a target of known type is not a finish node. Data outputs are exempt. Added to `ISSUE_CODES` (so the API, the contract and the MCP tools carry it) and shown in the editor like `FINISH_ORDER` ("not allowed here").
- **Existing workflows:** a saved workflow that fans out to non-finish nodes now shows an error (`OUTPUT_MULTIPLE_EDGES`), its active version is `runnable: false`, and queueing a run returns 422 `WORKFLOW_INVALID` instead of every job failing at run time.
- **Follow-ups (after review):**
  - Shared-output issues are now one per offending edge, with both `edgeId` and `nodeId`, and their codes are in the web's `EDGE_CODES`. So the editor draws those lines broken and badges the node. The message names the target (`…has 2 connections, one to Keep languages; …`), so two issues on one node read differently in the issues panel and over the MCP.
  - **`SIZE_GATE_SHARED_OUTPUT` (error, on the gate and its edge):** "The size gate must be the only step on this output; put the other steps after the gate's Yes or No." A gate among siblings would decide only for the steps wired after it, while the others ran whatever it decided. The walk refuses it too, at the gate. A bypassed gate decides nothing and may share.
  - **`OUTPUT_MULTIPLE_WRITES` (error, on each writing step and its edge):** two or more running write steps (Replace original, Move or copy) on one shared output.
  - **`NO_WRITE_PATH`:** finish nodes sharing an output count as one set, so a sibling of Replace original (a notify off the same Run node output, say) is no longer warned as "never writes the result".
- **Sub-workflows** cannot hold finish nodes, so a shared output inside one is always an error (validation and walk). A Run node's output in the parent may feed several finish nodes like any other.
- **Tests:** walk (three off Replace original in reverse wiring order; chains mixed with fan-out; same-phase nodes added in one order and placed in the other; wiring beats position; the gate's pass and else; Run node output; refusals), pipeline (run order and `problemsSoFar` after the write; two plugin steps on a failing gate's No), validation, and `engine/examples-walk.test.ts`, which walks every file in `examples/workflows` through `walkDecide`/`walkBuild` with fake plugin nodes (it reproduced the gate failure before the fix) and checks that no two same-phase finish nodes on one output share a canvas spot.
- **Same-phase order:** Sonarr or Radarr before Bazarr (both `library-manager`): `plugins.md` says to place Sonarr's rescan left of Bazarr's (or above it in one column).

## 2026-10-19 A restored original and its stale recycle row (gate finding C5)

- **The bug:** after an original is moved back from the recycle folder by hand (`mv -f .transcoda-recycle/<rel> <rel>`, the documented one-file rollback), its `recycled` row stays. A forced replace of that file moves the new original to the same recycle path, then fails to record it (`UNIQUE constraint failed: recycled.path`), recovers, and the job ends *done with a problem*. The row also kept the old job, size and time, so retention and the recycled bytes were off.
- **Decision: the new row replaces the stale one.** `insertRecycled` upserts on `path` and returns the row it replaced. A row for the same path can only be stale: the replace never moves an original onto a taken path, so a row there whose file is gone or changed was left by a manual move. Pruning stale rows up front was rejected: it would need a stat per row before every replace, and the upsert covers the only path where it matters. `recordRecycledRow` (`engine/recycle.ts`) logs one warning when it replaced another job's row: `replaced a stale recycle row; its original had left the recycle folder` with `path`, `job`, `staleJob`, `staleRecycledAt`. The replace (`durableReplaceWrites`, which now takes the logger), sidecar recycling and the startup sweep all use it; the sweep no longer skips recording when a row of an *earlier* job sits at the copy path (it did, leaving the stale row).
- **Decision: a restored original stays `already_processed`.** A `done` result's fingerprint is the original's (the replacement has its own and is walked again on the next run, ending `nothing_to_do`), so a match on a `done` result means the original is back. Making it eligible again was rejected: moving an original back is a rollback, and the next scheduled or folder-wide run would redo the change the person just undid. "A second run has nothing to do" holds either way. The job's reason now says what happened and what to do: `already done on <ISO>; this file is the original from before then (moved back from the recycle folder?); use Process again to run it anyway` (`alreadyProcessedReason` in `db/repos/jobs.ts`, used by the queue and by the pipeline's re-pin check). Other outcomes keep `already <outcome> on <ISO>`. The web's `reasonOf` keeps the text after `; `: "Processed on 1 Oct 2026: replaced; this file is the original …".
- **Docs:** `copy-run.md`'s rollback note said a restored file has a new fingerprint and is processed again; it does not, and now says so.
- **Open (for the owner):** the web's Run dialog has no force option, so "run with force" means the API (`force: true`) or the MCP tool. *(Resolved 2026-11-02, #40: Process again on the job and run pages queues with force; the reason now points at it.)*

## 2026-10-21 Plugin settings patterns never run on the server (sandbox review H2)

- **The problem:** the server built zod copies of a plugin's settings JSON Schema with `z.fromJSONSchema` (`plugins/settings.ts` for save/review, `nodes/remote.ts` for node settings, used by workflow validation, upgrade and the walk). A plugin-authored `pattern` became a `RegExp` run on the event loop: `^([a-f0-9]+)*X$` against 26 characters took ~12 s.
- **Decision: the server copy drops every regex-bearing keyword.** `serverSettingsSchema` (`nodes/plugin-settings-schema.ts`) removes `pattern`, `format` and `patternProperties` at every depth (a dropped `patternProperties` also drops an `additionalProperties: false` beside it, so keys it allowed stay allowed) before `fromJSONSchema`. Shape, type, required, enum, numeric and length bounds and defaults still apply. The host's validation with the plugin's own zod stays authoritative (it runs before every hook and on save while the plugin runs). Consequence: a save while the plugin is not running, and the server-side node settings check in the editor and validation, no longer report a pattern or format mismatch; the host's own zod checks them when the plugin next gets the settings. The schema reported to the web is unchanged (verbatim).
- **Backstop:** every string in the server copy is capped at 64 KiB (`MAX_SETTINGS_STRING`; a tighter plugin `maxLength` stays). A test fails if any other server file calls `fromJSONSchema`.

## 2026-10-21 A plugin cannot take the server down through its channel (sandbox review H1)

- **The problem:** the host shares an address space with the plugin bundle, and fd 3 (the IPC channel) is writable from plugin code (`--permission` does not gate writes to open fds). One malformed frame written there made Node's channel reader throw inside its own socket callback in the server: `Unable to deserialize cloned data` with `serialization: 'advanced'`. The server died, and died again on every boot while the plugin stayed enabled.
- **Not enough: `serialization: 'json'`.** Verified on Node 24.21: Node's json channel reader throws an uncatchable `SyntaxError` from the same callback for a non-JSON line, so switching serialization alone still crashes the server.
- **Decision: the server frames the channel itself.** `forkHost` spawns the host with a plain pipe on fd 3 (`stdio[3] = 'pipe'`, never `'ipc'`, no `fork`) and `NODE_CHANNEL_FD=3`, `NODE_CHANNEL_SERIALIZATION_MODE=json`, so the host keeps `process.send`/`on('message')` on a json channel (Node deletes both variables from the host's `process.env`). The server reads newline-delimited JSON in `plugins/channel.ts`; a line that is not JSON, or longer than `MAX_MESSAGE_BYTES` + 64 KiB characters, is a `bad-frame`. The protocol was JSON values already, so nothing is lost; the test harness (`testing/spawn.ts`) uses `json` too.
- **A bad frame stops that plugin for good:** new exit reason `protocol` (`broke the message protocol: malformed message frame: …`), the host is killed, a start fails with it, and the supervisor does not restart it (state `stopped`); the admin restarts or updates it.
- **Backstop in `main.ts`** (`process-guards.ts`): an unhandled rejection is logged and the server keeps running; an uncaught exception is logged with its stack and the server exits 1 after closing the database (its state is unknown).
- **Crash-loop guard** (migration 0012, `plugin_start_attempts`; numbered 0008 on its branch, renumbered after main's 0008–0011 when merging): each boot counts every enabled stored plugin it starts; a clean stop or `stableMs` (5 min) of uptime clears all counts, and enabling a plugin clears its own. A plugin counted `maxCrashes` (3) boots in a row is disabled in the database instead of started, with the state reason `disabled: the server stopped unexpectedly 3 times in a row while this plugin was starting or running; enable it to try again`. The server cannot tell which plugin killed it, so an unrelated crash loop within 5 min of boot disables every enabled plugin; that is the safe side. Dev plugins are not counted.

## 2026-10-21 The fetch proxy pins the address it checked (sandbox review M1)

- **The problem:** the proxy checked the origin as a hostname string and then let `http(s).request` resolve the name again on connect, and again on every redirect hop. A resolver that answers differently per lookup (DNS rebinding, or a compromised internal resolver) could point an allow-listed name at 127.0.0.1, 169.254.169.254 or the Docker network.
- **Decision: resolve once per hop, check every answer, connect to that address.** `FetchProxy.pin` resolves the hop's host (`dns.lookup`, `all: true`), refuses the request if any answer is forbidden, and answers the socket's `lookup` with the checked address; the url keeps the name, so Host, TLS SNI and certificate checks are unchanged. IP literals are checked without a lookup. A 429 retry and each redirect hop are pinned afresh. Classification lives in `plugins/address-policy.ts`.
- **Policy (behavior change):** loopback (127/8, ::1, 0.0.0.0/8, ::, IPv4-mapped/NAT64 forms), link-local (169.254/16, fe80::/10), cloud metadata (169.254.169.254, 100.100.100.200, fd00:ec2::254) and multicast/reserved are always refused (`refused`, `<host> resolves to …`). Private ranges (10/8, 172.16/12, 192.168/16, 100.64/10, fc00::/7) are allowed only when the allow-listed origin's host is itself private: a private IP literal, a single-label name (Docker service) or a LAN suffix (`.local`, `.lan`, `.home`, `.home.arpa`, `.internal`, `.intranet`, `.localdomain`, `.corp`, `.private`, `.ts.net`). The allow-list stays the boundary; this only narrows it. Consequences: an integration configured as `http://localhost:8989` or `http://127.0.0.1:…` no longer works (use the host's LAN address), and a public name served by split-horizon DNS to a LAN address is refused (use the LAN name or IP).
- Tests stand a loopback server in for a LAN or public one through `FetchProxyDeps.classify`/`resolve` (`PluginServiceDeps.fetchAddresses`); production never sets them.

## 2026-10-21 Plugin memory and slot caps (sandbox review M2, M4)

- **The problem:** nothing bounded how many plugin hosts ran at once (N enabled plugins = N processes of up to `rssMb` each), `plugins.limits.rssMb` accepted up to 8192, the shipped compose had `mem_limit` commented out, and a canceled call whose plugin ignored `cancel` kept its host (and its memory) until the call's full timeout (30 s, 5 min for a finish `run`).
- **Decision: a cap on live hosts.** New limit `maxHosts` (default 16, settings row `plugins.limits.maxHosts`, at most 256). `PluginSupervisor.launch` counts other plugins with a live process (one in restart backoff does not count) and refuses the start past the cap: state `stopped`, reason `too many plugins running (at most 16); disable another plugin or raise plugins.limits.maxHosts`, returned as a `bad-manifest` start error like the other refusals. It is not retried by itself (a crash restart that finds the cap full stops too); enable or restart the plugin once a slot is free. A candidate (update) of a running plugin replaces its process and is allowed at the cap; one for a stopped plugin needs a free slot.
- **Decision: `rssMb` is bounded at 2048** (was 8192); a stored value above it falls back to the 256 MB default. `heapMb` keeps its bound of 4096 (an RSS kill comes first anyway).
- **Decision: a canceled call gets a short grace.** New limit `cancelGraceMs` (default 5 s, at most 60 s). On cancel, `PluginProcess` replaces the call's timeout with a reaper at `min(cancelGraceMs, time left on the call)`; an answer in that window disarms it, otherwise the host is killed (exit reason `timed out after 5 s in <hook>`, warning `cancelled plugin call did not stop within its grace period`) and the supervisor restarts it as after any timeout. Behavior change: a plugin that keeps working after its job is canceled for more than 5 s is now restarted instead of being given the full call timeout.
- **Compose:** `docker/docker-compose.yml` ships `mem_limit: 4g` with the sizing formula (server ~512 MB + 256 MB per enabled plugin + ffmpeg); the README snippet and `docs/env.md` say so. The owner's deploy compose keeps its own 3g.

## 2026-10-21 Signed catalog index is monotonic (sandbox review L1)

- **The problem:** the catalog verified the signature over the index bytes but not its age, so whoever controls the network path could replay an older validly signed `index.json` to hide an update or offer an older signed build.
- **Decision: mirror the blocklist.** For a catalog with signing keys, a freshly fetched and verified index whose `generated` is older than the cached verified index's is refused: the cache is not overwritten, the cached index keeps being served, the listing carries the error `catalog index older than the cached one (generated <new>, cached <old>)`, and the server warns `refused a catalog index older than the cached one`. An equal `generated` is accepted. Unsigned catalogs are unchanged (they have no integrity to protect). Limit: the first fetch, or one after the cache is cleared or tampered with, has nothing to compare against.

### The binding

- **The active version's Library input is the one binding between a library and a workflow.** `libraries.default_workflow_id` is gone. ## 2026-10-21 Backup on build change

- **The gap:** a database was backed up only before pending migrations. An update without a migration still changes data at start (workflow upgrades run right after `migrate`), with no copy to go back to.
- **Decision: back up when the build changes.** In `createDeps`, right after `migrate` and before anything else writes (plugin start, workflow upgrades, the engine's sweep), `backupOnBuildChange` (`db/build-backup.ts`) compares the build id with the `app.lastBuildId` settings row. Different, or no row while the database already existed (`migrate`'s `from > 0`: an install from before this check): a `VACUUM INTO` backup into the same `backups/` folder, pruned with the others (`KEEP_BACKUPS`, see the review fixes below), one log line `Build changed (<old|none> → <new>); backed up database to <file>`. Then the new id is stored. No backup when `migrate` took one this start, or for a brand-new database. A failed backup stops the start, as a failed migration backup does. The id is stored after the backup, so the backup holds the old id: restoring it and starting the same build backs up once more, which is harmless.
- **Build id:** `TRANSCODA_BUILD_ID` when set (the image has an optional `TRANSCODA_BUILD_ID` build-arg, empty by default; 1-64 of `[A-Za-z0-9._-]`, else a `ConfigError`), else the first 12 hex characters of the sha256 of the running server file, resolved from `import.meta.url` in `bootstrap.ts`, which in the image is the single bundle `/app/server/main.js`. The version is `0.0.0` until releases and the image is built from `git archive` (no `.git`), so neither can tell builds apart; the hash changes with every server code change and needs nothing from CI. A web-only or plugin-host-only change keeps the id (neither writes the database). From source (`pnpm dev`) the hashed file is `bootstrap.ts` itself, so dev starts rarely back up; set `TRANSCODA_BUILD_ID` to force one. An unreadable file logs a warning and skips the check.
- **Names:** the format stays `transcoda-<YYYYMMDD-HHmmss>-v<schema>.sqlite`; build-change backups add `-build`, manual ones `-manual` (`v` is the current schema for these, the schema before the migration for migration backups). A name already taken gets `-2`, `-3`, …, so a second backup within the same second never fails on `VACUUM INTO` (fixes the per-second known issue). `listBackups` sorts by the stamp, then the counter (no counter counts as 1), then the name, so pruning stays oldest-first across reasons; names it cannot parse sort by their text as before.
- **API and UI:** `system.backups.list` (`GET /system/backups`, `read` scope) returns `{ backups: [{ name, size, createdAt, reason }], keep }`, newest first, file names only (never a server path). `system.backups.create` (`POST /system/backups`) takes a `-manual` backup; `requireHumanSessionWith('Backups are taken in the UI')` refuses every API token, and there is no MCP tool. `createdAt` is read from the stamp in the name (local time), not the file's mtime. Settings → About shows a Database backups panel: each file's name, reason (Before migration, Build change, Manual), size and time, **Back up now**, and the restore steps (stop the container, copy the backup over `transcoda.sqlite`, delete `-wal` and `-shm`, start). `docs/env.md` has a Database backups section with the same steps.
- **Review fixes (same day):** pruning keeps 5 *per reason* (migration, build, manual), so build-change or manual backups never evict the pre-migration copy that `SchemaTooNewError` points to. Backups are atomic: `VACUUM INTO ?` (a bound parameter, no interpolated path) writes `<name>.part` (which `BACKUP_PATTERN` does not match), the file is fsynced and renamed into place; on failure the `.part` is removed and the error rethrown, and a stale `.part` from a crash is removed before the next attempt. `system.backups.create` refuses a second manual backup within 30 s (`RATE_LIMITED`, "A backup was taken moments ago; try again in N s"; per app instance, in memory). The panel's button uses `aria-disabled` while a backup runs (focus stays), the "Backed up to <name>" line is visible, and a rate-limit refusal shows the server's message.
- **Download (same day, the owner's request):** `GET /api/v1/system/backups/<name>/download` is a plain Hono route beside the contract (`http/backup-download.ts`; it streams a file, which the contract's JSON procedures do not), so it is not in the OpenAPI spec or the RPC client. A backup is treated like the database: session only (token → 403 "Backups are downloaded in the UI", no MCP tool), no CSRF header for the GET but the cookie is `SameSite=Lax` and `sameOriginOk` refuses `Sec-Fetch-Site: cross-site` or a foreign `Origin`, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`. `findBackupFile` serves a name only when it matches `BACKUP_PATTERN`, is made of `[A-Za-z0-9._-]` without `..` (also keeps `Content-Disposition` safe), is in `listBackups` (so never a `.part`), resolves directly inside `backups/` and is a regular file; anything else is a 404 with no detail. Hardening after review: the file is opened with `O_RDONLY | O_NOFOLLOW` and checked with `fstat` on that fd (regular file, size for `Content-Length`), then streamed with `createReadStream('', { fd, autoClose: true })`, so a symlink or other file swapped in after the name checks is refused at open (no check-then-read race). HEAD (which Hono answers with the GET handler, dropping the body uncancelled) closes the fd at once and returns headers only, so it never leaks a descriptor. The panel has a Download link per row, a note that a backup holds the password and token hashes and the plugin secrets (keep it private; plugin secrets are AES-256-GCM under a key derived from `secret.key`, not in the backup, so unreadable without it), and the restore note now says to restore next to the same `secret.key`.
- **`SchemaTooNewError` hint:** names the newest *migration* backup (the copy from before the upgrade that made the schema too new); only when there is none, the newest backup of any kind, since a build-change or manual backup may already be at the newer schema.
- **Not done:** no delete or restore from the UI; restoring stays a manual step with Transcoda stopped.

## 2026-10-21 Test-encode dry runs

- **What stops where.** A test-encode dry run (`testEncode` on the run and job) runs probe → decide → build → encode → verify → measure for real, with the same encoder and the same verify checks as a real run, into the job's temp dir under `TRANSCODA_TRANSCODE_DIR`. Reaching the first write, or the end of the list, ends it `dry_run` ("would replace"). Every writing step (replace, move-copy, sidecar recycle, notify, `afterReplace`) now throws if a dry run ever reaches it, so a future walk bug fails the job instead of writing. ## 2026-10-22 NVENC encodes decode on the GPU

- **Why.** On the owner's server (4 cores, RTX 3060) the GPU looked idle: Beszel shows the shader load, which NVENC is not part of, and NVENC waited on the CPU's H.264 decode. Measured with jellyfin-ffmpeg 8.1.3 on a 1080p AVC remux, 60 s, NVENC `-cq 20`: CPU decode 10.5x at about 3 cores; `-hwaccel cuda` 15.7x at 0.1 core (frames on the GPU) and, for the whole job with two DTS-HD → AAC tracks, 7x → 11.8x with 2.7 → 1.6 cores.
- **Rule.** `renderArgs` puts `-hwaccel cuda` before the source's `-i` when a converted video stream uses an `*_nvenc` encoder, unless the model's `globalArgs`/`inputArgs` already name a `-hwaccel` (then that one stands). Without `-hwaccel_output_format cuda` the decoded frames come back to system memory, so `-pix_fmt` and filters render as before; ffmpeg decodes on the CPU when the GPU has no decoder for the codec (checked with an MPEG-4 Part 2 source). QSV and VAAPI are unchanged.
- **Not done.** Keeping frames on the GPU (`-hwaccel_output_format cuda`, `scale_cuda` for pixel formats) saves the copies too but breaks CPU filters and has no CPU fallback; worth it only if the copy shows up as the limit.

## 2026-10-22 Encoding device setting

- **Where.** One global setting, Settings → Queue and engine → "Encoding device" (`engine.encodeDevice`): `auto` (default, as before), `cpu`, or `nvidia:<index>`. Not per workflow: a GPU index belongs to the machine, and workflows are exported and shared. A node that must stay on the CPU already can (its encoder setting, e.g. `libx265`).
- **Effect.** The setting filters the capabilities Encode video and validation see (`effectiveCapabilities`): `cpu` drops every hardware encoder and hwaccel, so `auto` picks software and a node that names `hevc_nvenc` is ENCODER_UNAVAILABLE; `nvidia:<n>` keeps NVENC and CUDA only and renders `-hwaccel cuda -hwaccel_device n` plus NVENC `-gpu:<i> n`. `auto` renders no device index, so a one-GPU or no-GPU machine gets the argv it had. The device is read when a job is prepared.
- **Decoding follows encoding.** No separate setting: a job decodes on the device it encodes on (with the CPU fallback of 2026-10-22 "NVENC encodes decode on the GPU").
- **Detection.** `nvidia-smi -L` at startup (`capabilities.gpus`); none detected but NVENC present counts as an unnamed GPU 0. The server sets `CUDA_DEVICE_ORDER=PCI_BUS_ID` (unless set) so ffmpeg's CUDA index is nvidia-smi's. A stored GPU that is no longer found acts as CPU only, and Settings says so.
- **Not run on a GPU.** The `-hwaccel_device`/`-gpu` flags are covered by render and pipeline tests only.

## 2026-10-23 Several GPUs encode in parallel

- **Slots.** The encode lane has encode slots (`encodeSlots` in capabilities/devices.ts, asked at every grant): with "Encoding device" `auto`, two or more GPUs from `nvidia-smi -L` and NVENC in ffmpeg, one slot per GPU (`gpu:<index>`); otherwise the one slot of before, on the pinned GPU if the setting names one. The quick lane is unchanged. Jobs keep `lane = 'encode'` on their row.
- **Device per job.** Build renders the argv before a slot is known; `execute` gets the slot's device and renders it again (`-hwaccel cuda -hwaccel_device n`, NVENC `-gpu:<i> n`), so the stored command names the GPU. A software encode takes any free slot: its argv gets no device flags, and the number of encodes at once stays the number of GPUs.
- **Pause.** A job the user paused gets its own slot back (its ffmpeg runs on that GPU); other slots go on to other jobs meanwhile. If its slot is no longer offered (the setting changed), it takes any free one. A slot no longer offered stays in the status while a job runs in it.
- **Status.** `queue.status` and `queue.changed` carry `encodeSlots: [{ id, label, jobId }]`; `lanes.encode` stays, as the first busy slot, for older clients. The queue bar names each GPU when there are several ("GPU 0 · RTX 3060: movie.mkv · GPU 1 · RTX 3060: idle · Quick lane: idle"); Settings → Lanes reads "Encode ×2 (one per GPU)".
- **CPU only and a named NVENC encoder** stay an error (ENCODER_UNAVAILABLE), as of 2026-10-22.
- **Not done.** QSV/VAAPI devices are neither listed nor scheduled per device: the render passes no VAAPI device or `hwupload`, so `*_vaapi` likely does not run at all yet. "Jobs per GPU" (more than one NVENC session per card) is left for later.
- **Not run on hardware.** No multi-GPU machine was available; the scheduler and argv are covered by tests only, and CUDA's PCI-bus order matching nvidia-smi is from NVIDIA's documentation, not observed.

## 2026-10-22 Remove duplicate audio

- **Node.** `core:remove-duplicate-audio` ("Remove duplicate audio", version 1, action, icon `copy`, no settings) works on the build model as planned so far. Meant to follow Encode audio: a film with TrueHD 5.1 and AC-3 5.1 640k in English, both encoded to AAC 2.0 160k, keeps one AAC track.
- **Duplicates.** Two kept audio tracks are duplicates when what they write has the same language (normalized; untagged and `und` are one value of their own, never a match for a real language), the same codec and the same known channel count (a converted track's target codec and channels, else the source's; a copied track's probe codec and channels; an unknown count matches nothing), the same forced flag, the same title words (below), and, for copied tracks, the same sample rate and bit depth (unknown is a value of its own; a conversion's are what the encode makes, so they only rank the sources); and neither is special. Special: a `comment`, `visual_impaired`, `hearing_impaired`, `karaoke` or `dub` disposition, or a title word starting with comment, descri or narrat, or the word AD. Bitrate is not compared. All of this is one key per track, so "duplicate" is an equivalence and the groups never depend on track order.
- **Titles (review fix, same day).** Two titles match only when their meaningful words are equal; there is no wildcard, so an untitled track matches only a title that strips to nothing. Stripped: whole format names (`Dolby Digital Plus`, `Dolby Digital`, `TrueHD`, `DTS-HD MA`, `DTS:X`, `DD+`, `E-AC-3`, `AC-3`, `HE-AAC`, `640 kbps`, `48 kHz`, `24-bit`, …), single codec and layout words (Dolby, DTS, AAC, AC3, Atmos, FLAC, PCM, stereo, mono, surround, …), plain numbers, and the track's language name and codes. Ordinary words that also occur inside format names (master, true, plus, digital, audio, x, es) are kept when they stand alone: stripping makes tracks more alike, so a doubtful word stays. So "Theatrical (DD+ 5.1)" = "Theatrical", "English DTS 5.1 1509 kbps" = no title, while "Audiodeskription", "Hörfilm", "Kommentar", "Isolated score" or "Music only" never go for an untitled main track (the first version treated an empty title as matching any title, which dropped those).
- **Added copies (review fix).** A kept plan that copies the same source stream as an earlier kept plan (Encode audio's add-track copy) is left out entirely: it exists so a target can play the default, it is never dropped and never makes another track a duplicate.
- **Which one stays.** The one made from the best source: lossless (truehd, mlp, flac, alac, `pcm_*`; dts only with a DTS-HD MA profile) before lossy, then more source channels, then higher bit depth, then higher sample rate, then higher bitrate (unknown lowest in each), then the earlier track in output order. When a dropped track was default and no kept audio track is default after the drop, the kept track of its group becomes default (the reason ends `; default audio now audio #1`); otherwise flags stay as they are and the usual normalization applies.
- **Words.** Tracks are named `audio #N`, N their place among the source's audio tracks (as the job page names them). Reason: `dropped audio #2: same as audio #1 (AAC 2.0 English)`, joined by `; `; with nothing to drop `no duplicate audio` (a no-change step). The plan's note for the dropped stream is `same as audio #1 (AAC 2.0 English)`: `StreamPlan` gains an optional `dropReason`, which `diffFromProbe` uses in place of the language on a drop line. `findings.dropped` lists `{ index, sameAs, codec, channels }` per dropped track (source indices and what it would have written). Job page: `Drops audio #2 (AC-3 5.1 → AAC 2.0): same as audio #1` (several tracks with the same keeper in one clause, `; ` between keepers, `; English audio #1 becomes the default` when the flag moved), `No duplicate audio tracks` when nothing goes.

## 2026-10-22 Verify progress

- **What verify does.** It is not one ffmpeg pass: an ffprobe of the output, bounded packet reads at each output media stream's end (against the source's), decode of the first second, of the end from a keyframe, and of ~10 one-second spots, then (library `verifyFullDecode`) a decode of the whole output. After a decode failure the source is decoded at the same spots. Measured on a 10 min 1080p HEVC file (M-series Mac): each spot decode ~0.2 s, each read ~0.05 s, the checks ~2 s in all; the whole-file decode ~8 s, so minutes on a film or a busy box.
- **What is shown.** The checks are counted, not given as a percent (a probe read and a decode are different amounts of work): `job.progress.verify` = `{ stage: 'checks', done, total }`, total = 1 probe + one per output media stream end + decode start and end + the sampled spots (a spot that cannot be opened counts as done). The bar and the node fill follow `done / total`; the words say `Verifying · 3 of 14 checks` (node, header) and `Checking duration, streams and decode · 3 of 14 done` (detail). The whole-file decode has real progress: ffmpeg `-progress pipe:1` (through `Exec`'s new `onStdout`), its out time against the output's duration, as an encode (`Verifying · whole file 43%`, `Decoding the whole file · 43% · 412 fps · ETA 4 min`), written at most once a second. Re-decoding the source has no measure: `stage: 'source'`, words only (`Verifying · checking the source`), no fill. Replacing starts with no progress.
- `JobProgress.verify` is optional, so encode progress and rows written before it parse as they are. The Jobs list's row bar shows for verifying too; the phone card and the activity ring stay encode only (their head reads the percent as a bare number).

## 2026-10-22 Encode bitrate control

- **Settings.** `core:encode-video` and `core:encode-audio` are at version 2. Encode video gains `rateControl` (`quality`, the default and the old behavior, or `bitrate`) and `bitrateKbps` (100–200 000, default 6000, used only in bitrate mode); both nodes gain `neverIncreaseBitrate` (default `true`). Migration 1→2 (risk `safe`) sets `neverIncreaseBitrate: false` on a saved node that does not say, so existing workflows encode exactly as before; new nodes, the examples and the TV cleanup example get the cap.
- **Cap, not skip.** The engine plans the whole ffmpeg run before it encodes and writes every stream in that one pass, so "keep the original stream when the encode came out bigger" would need a second encode (or a whole-file keep-original, which the Size gate already is). So the cap is planned: a target bitrate above the source is lowered to it, and quality mode gives the encoder the source bitrate as a ceiling. Audio always knows both numbers, so a track is encoded at `min(set bitrate, source bitrate)`.
- **Source bitrate.** The probed stream's `bit_rate`, else mkvmerge's `BPS`/`BPS-<lang>` statistics tag (probe now reads it), floored to whole kbps. Video falls back to the file's bitrate (an upper bound, as in Video is); the reason says `the whole file's bitrate`. Unknown → no cap, and Encode video's reason says `source bitrate unknown, not capped`. Audio without a known source bitrate is not capped and says nothing (lossless sources mostly).
- **Model.** No new `StreamPlan` field: on video, `bitrateKbps` alone is a target bitrate and `quality` + `bitrateKbps` is capped quality.
- **Rendering (ffmpeg 7.1 sources checked).** Target bitrate: `-b` on every encoder, NVENC with `-rc vbr`, VAAPI without an rc_mode (ffmpeg tries AVBR, VBR, CBR). Capped quality: x264/x265/SVT-AV1 `-crf` + `-maxrate`/`-bufsize` (2× the rate; x264 ignores a maxrate without a buffer); libaom `-crf` with `-b` = the cap (constrained quality instead of `-b 0`); NVENC `-rc vbr -cq <q> -b 0 -maxrate -bufsize` (constqp ignores a maxrate); QSV `-global_quality` with `-b` 1k under `-maxrate` (QVBR; an equal pair selects CBR); VAAPI `-global_quality -b -maxrate` without rc_mode (QVBR where the driver has it, else ICQ/CQP at the quality, uncapped). Quality alone renders as before.
- **Measured (ffmpeg 9.0.2, 30 s 640×360 test source re-encoded from 300 kbps, cap 300k):** x265 crf 18 → 307 kbps, x264 crf 12 → 307 kbps (container overhead included), SVT-AV1 crf 12 → 365 kbps (uncapped 2.2 Mbps; SVT-AV1's max bitrate is a soft cap, a smaller buffer does not tighten it). Target bitrate x265 200k → 200 kbps. libaom was not available locally.
- **Not verified on hardware.** The NVENC/QSV/VAAPI flags follow ffmpeg's rate-control selection code; no GPU run was done.
- **Wording.** Reasons and the plan diff name a capped NVENC quality `cq` and a capped VAAPI one `q` (`qualityName(encoder, capped)`, shared by the diff and Encode video's reason); the diff writes the ceiling as `max 5000k`, a target bitrate as `3000k`. The job page says `in software (libx265, 3000 kb/s)` and `on the GPU (NVENC, CQ 24, at most 5000 kb/s)`.
- **Editor.** The schema fields carry the labels and hints ("Rate control", "Quality (CRF)", "Target bitrate (kbps)", "Never above the source bitrate"). ## 2026-10-26 Intel GPUs and GPU order

- **Why.** The owner added an Intel Arc A310 next to the RTX 3060. A new show drops 100+ episodes into the queue; both cards should work through them, NVIDIA first, Intel only when NVIDIA is busy. Design: `docs/plans/2026-10-26-gpu-priority-design.md` (git-ignored).
- **Detection.** NVIDIA GPUs come from `nvidia-smi -L` as before. Intel GPUs are the DRM render nodes (`/sys/class/drm/renderD*`) whose PCI vendor is `0x8086` and that the server can open, sorted by PCI address. Names come from a small device-id table (`56a6` = "Intel Arc A310"), else "Intel GPU <id>". No `/sys/class/drm` (macOS, some containers) means none. `Gpu.vendor` is `nvidia | intel`; Intel GPUs carry `renderNode` and `pci`.
- **Ids.** Setting ids: `auto`, `cpu`, `nvidia:<index>`, `intel:<pci address>` (`intel:0000:07:00.0`); "Encoding device" can pin an Intel GPU like an NVIDIA one (effective capabilities then keep QSV only). Slot ids: `gpu:<index>` (NVIDIA, unchanged) and `gpu:intel:<pci>`. Labels: `GPU 0 · NVIDIA GeForce RTX 3060`, `Intel Arc A310 · 07:00.0`. Stored values from before stay valid; migration 0013 only adds the job's `encoded_on` and `failed_gpus`.
- **Order.** `engine.gpuOrder` (Settings → Queue → GPU order, Move up/down) lists GPU ids; the default (empty) is NVIDIA by index, then Intel by PCI address. Ids no longer detected stay in the list, marked "(not found)". Under Auto with two or more usable GPUs (NVIDIA with NVENC, Intel with a QSV encoder) there is one encode slot per GPU in that order (`Encode ×2 (one per GPU)`); otherwise the one slot of before. NVENC without nvidia-smi counts as an unnamed GPU 0, so that setup stays on NVIDIA by default.
- **Fit.** Prepare says what a job needs (`slotFitOf`): `gpu` (an auto-picked hardware encoder, any GPU), `nvidia` / `intel` (a named `*_nvenc` / `*_qsv` encoder, that vendor only; also an auto job that cannot move to the other vendor, because this ffmpeg lacks that encoder or the moved model cannot render), `software`. A waiting `gpu` job takes the first free slot in GPU order; a named job the first free slot of its vendor, and waits for one while a `gpu` job behind it takes the other GPU; a software job takes the last free slot, so it leaves the first GPU to GPU jobs. Look-ahead keeps preparing while a free slot has no ready job that fits it.
- **Auto-pick tracking.** Build still resolves Auto in the old order (NVENC → QSV → VAAPI → software), whatever the GPU order, so a preview may name NVENC for a job that then runs on the Arc. The walker records which streams an `encoder: auto` Encode video picked (server-side, per stream; no SDK change). At Execute, when the slot's vendor differs, those streams swap to the slot vendor's encoder for the same codec (`hevc_nvenc` ↔ `hevc_qsv`, `h264_nvenc` ↔ `h264_qsv`), presets map (`p1`–`p7` → QSV `veryfast`…`veryslow`; QSV `veryfast`/`faster` → NVENC `fast`, `slower`/`veryslow` → `slow`), pixel formats map to `nv12`/`p010le`, quality and bitrate stay, and the plan is recomputed so the job page names what ran. A named encoder never moves; a plugin hook that changes the encoder makes the stream not auto. QSV profiles: `hevc_qsv` main/main10, `h264_qsv` baseline/main/high.
- **Known limits of the inference.** A workflow with two Encode video nodes on one path, Auto and then a named encoder equal to Auto's pick, is treated as auto (the named stream may then move to the Arc). An Auto node that lands on the encoder an earlier named node already set records no pick, so that stream stays where it is (fails safe).
- **Encoded on.** The job records the GPU it encoded on (`encodedOn`, "Encoded on" on the job page): the slot's label, or for the one plain slot the pinned GPU's name (fixed on a dev box: it read "Encode"). Null for a software encode, a slot without a device, or the other vendor's encoder.
- **A failed GPU tries another GPU first** (the owner). A GPU failure (`looksLikeGpuFailure`; now also libvpl/MFX errors and a render node that cannot be opened: "No VA display found for device …", "Device creation failed") sends the job back to the queue with that GPU in `failedGpus` and a warning ("<GPU> failed (…); trying another GPU"); placement skips the failed GPUs. Only when no other GPU fits does it fall back to software in place, as before. A software fallback after the last GPU does not add that GPU to `failedGpus`, so an automatic attempt 2 gives each GPU one more try. "Retry failed" clears the list. A job whose failed GPUs cover every slot it may use (after a settings change) is placed ignoring the list, so it is never stranded.
- **QSV flags (checked on the A310, ffmpeg 8.1.3-Jellyfin).** Every QSV encode on an Intel slot opens that GPU: `-init_hw_device qsv=qsv:hw,child_device=/dev/dri/renderD128 -filter_hw_device qsv`, unless the model brings its own `-init_hw_device` or `-hwaccel` (then its setup stands, as for NVENC, and the QSV encoder uses ffmpeg's default Intel device). When every converted video stream is QSV-encoded from the source at a known 8- or 10-bit 4:2:0 format and the model brings no device or hwaccel of its own, the source also decodes on the Arc and stays in GPU memory: `-hwaccel qsv -hwaccel_output_format qsv`, and `-pix_fmt` becomes `-filter:<i> vpp_qsv=format=nv12|p010`. Otherwise the source decodes on the CPU as before. Checked on a dev box: H.264 8-bit → HEVC main and main10, HEVC 10-bit → HEVC main10 (stays 10-bit) and → H.264 high, MPEG-4 (no hardware decoder; ffmpeg decodes it on the CPU and vpp_qsv takes the frames). A 4:2:2 H.264 source fails in the QSV decoder ("Error querying IO surface"), which counts as a GPU failure: another GPU; with none left, the same Intel GPU once more with the source decoded on the CPU (any GPU failure of a job that decoded into GPU frames, once per attempt, with a warning); then software. Rejected: `-hwaccel qsv` without an output format (ffmpeg then defaults to GPU frames and the CPU scaler fails), `-hwaccel_output_format nv12` (fails on 10-bit: "Error synchronizing the operation: -16"), and VAAPI decode with frames back in system memory (works, but on the A310 it cost more CPU than decoding on the CPU: 63–68 s user time against 53–56 s for a 24-min 484×360 episode, because frames go down and up again).
- **Measured (a dev box, 4 cores, 3060 + A310; the owner's server was encoding on the same host and the same 3060 throughout, host load 17–28, so job times vary by ±30 %).**
  - Encoders alone, two 4-min 1080p H.264 episodes (10 Mbit/s): the 3060 one after the other 55.6 s and 52.9 s; the 3060 and the Arc together 28.4 s and 23.5 s (the Arc's episode 15.2 s and 14.3 s); with the Arc decoding on the CPU, as first built, 52.9 s and 41.0 s. The owner's own measurement on a 1080p H.264 Blu-ray source under load: CPU decode then hevc_qsv 2.51× realtime, the GPU path 14.3×; with the CPU decode the Arc job took ~250 % CPU and the NVENC job's encoder load fell from ~100 % to ~50 %.
  - Whole jobs (test encodes through the queue), same pair: with the library's whole-file decode check, 3060 alone 142 s and 168 s, Auto 126 s and 187 s (the box is CPU-bound by the verify decodes: 2–8 % idle); without it, 3060 alone 58 s and 78 s, Auto 53 s and 55 s.
  - Low-resolution dev episodes (24-min 320×240 and 484×360), CPU decode on the Arc: 3060 alone 79, 66, 50 s, Auto 65, 65, 70 s; with the GPU path: 3060 alone 51, 64, 95 s, Auto 57, 72, 76 s. These jobs are verify- and CPU-bound, so a second GPU does not shorten them.
  - So the pass rule holds for the encode itself and for jobs without the whole-file check; with it, the CPU (verify decodes on 4 cores) is the limit. CPU during Auto pairs: 2–15 % idle in the CT.
- **Load graph.** Intel load comes from the i915 per-client counters in `/proc/<pid>/fdinfo/<fd>` (`drm-engine-video`, busy ns over wall ns, every 5 s), for the ffmpeg processes visible in Transcoda's own PID namespace (`/proc/<pid>/comm` is `ffmpeg`): its own encodes only, not other users of the card, and on a bare-metal install the scan skips every other process. Encoder and decoder share that engine, so one "video" line. An idle Arc has no graph line until its first encode. No privileges and no `intel_gpu_top` (it needs perf events; the host has `perf_event_paranoid = 4`).
- **Queued jobs follow the activation** (checked on a dev box). Six real jobs with a version naming `hevc_nvenc`; while the first encoded, a version with `encoder: auto` was saved and activated. The five that had started preparing ran on the old version on the 3060; the one still queued re-pinned to the new version and ran with `hevc_qsv` on the Arc, at the same time as the 3060's. ## 2026-10-28 Already processed

- **Why.** The owner wanted a condition that answers "has this file already been through workflow X?" in the graph. The queue's own `already_processed` skip only knows the source fingerprint of the same workflow version, and after a replace the file on disk is the output, with a new fingerprint: nothing knew it as Transcoda's output.
- **Output fingerprint.** `job_results.output_fingerprint` holds the `fingerprintKey` of the file the job left at its final path, read once every finish step ran: the replaced original, or the last move-copy destination (the copy for copy, the moved file for move). Only `done` results carry it; null when nothing was written or the file is gone by then (a plugin step may move it). The startup sweep that finishes an installed replace records it too. A replace keeps the original's mtime, but the inode and size are the output's, so the key differs from the source's. It is free and matches the very file the job left.
- **Content hash.** `job_results.source_hash` (every real job, taken right after the source's fingerprint at prepare; dry runs record none) and `output_hash` (done results, next to `output_fingerprint`) hold a sampled content hash (`engine/content-hash.ts`): `v1:<size>:<sha256 hex>`, where the sha256 covers the scheme, the size and three 4 MiB chunks at the start, the middle (`floor((size - 4 MiB) / 2)`) and the end. A file of 12 MiB or less is hashed whole. Only those chunks are read, never the whole file; the hash is canceled with the job, and a file that is gone (or shrinks while read) has none. The `v1` prefix lets the scheme change later: an old hash then just never matches. 4 MiB per chunk: the start and end cover the container's headers and index (Matroska segment info and cues, MP4 `moov` at either end) and the middle a run of media packets, so two encodes of one source differ in what is read, while a file costs 12 MiB of reads (milliseconds locally, about 0.1 s over gigabit). It recognizes identical copies and re-downloads at any path, across moves and filesystems, where the fingerprint (inode, mtime) cannot. Bytes outside the three chunks are not seen: two files that differ only there hash the same, which for media files of the same size and identical headers, index and middle is taken as the same file.
- **Why not a tag.** A first version wrote a `TRANSCODA` container tag naming the workflows. On MP4 a custom tag needs `-movflags use_metadata_tags`, which moves every global tag into `mdta` keys, so the title left the iTunes `©nam` atom Apple, Plex and Jellyfin read; and files a workflow left untouched (`nothing_to_do`, `kept_original`) were never tagged. The hash needs no change to any output: files are written exactly as before.
- **Indexes.** Migration 0015 adds the three columns and partial indexes on `(output_fingerprint | source_hash | output_hash, workflow_id, workflow_version)`.
- **The node.** `core:already-processed`, "Already processed", a condition with Yes (`pass`) and No (`else`). Settings: `workflowId` (absent: "This workflow") and `version` (absent: any version). Yes when a real job of that workflow (at that version, if set) ended `done`, `nothing_to_do` or `kept_original` and (a) the file's fingerprint is its source `fingerprint` or its `output_fingerprint`, or else (b) the file's content hash is its `source_hash` or `output_hash`. The hash is computed only when the fingerprint found nothing (a real job's source hash from prepare is reused; a dry run hashes once, when a node first asks). `failed` never counts (a failed file should be able to run again), dry runs never count, and the asking job's own result is left out. Reasons: `done by Save space v3 on 2026-10-28 (this file is its output)`, `… (this file is its original)` (the original came back from the recycle folder), `nothing to do for Save space v1 on …`, `original kept by …`, and by hash `… (same content as its output)`, `… (same content as its original)`, `… (same content as the file it checked)`; `not processed by Save space v2`. The date is the server's local calendar day (`TZ`); findings carry the full time, the job id, the evidence (`fingerprint` or `hash`) and whether the source or the output matched.
- **"This workflow" in a sub-workflow.** Results are recorded for the workflow a job runs, never for a sub-workflow, so "This workflow" always means the job's own (top-level) workflow, and a version means that workflow's version, the one the job runs at. A node inside a sub-workflow used by two parents therefore asks each parent about itself. Picking a sub-workflow explicitly is not offered.
- **Editor.** Its own inspector, like Run sub-workflow's: a picker with "This workflow" and the other workflows by name (a deleted one stays selected as "(no longer exists)"), and "Any version" or v1…vN of the chosen workflow; inside a sub-workflow "This workflow" has no known version list, so the version is a number to type. MCP agents get the settings schema from `list_nodes` like any core node.
- **Not done.** No validation issue for a `workflowId` that no longer exists (the node answers No and names the id). The queue's own `already_processed` skip still uses the source fingerprint only. Results from before this change have no hashes.

## 2026-10-29 File inputs take several connections

- **Why.** The owner: a workflow that replaces a damaged file can reach that step on several paths (Check source's Damaged, Render's Damaged), and the editor made him place the node once per path.
- **Rule by port type.** Every `file` input takes any number of incoming edges; every `data:*` input keeps the limit of one. No per-port flag, no SDK, contract or plugin change, no graph format bump or migration: graphs that showed `INPUT_MULTIPLE_EDGES` on a file input simply become valid.
- **Why it is safe.** A file follows exactly one path per run: a condition picks one output, and a size gate's `else` and Render's Damaged are exclusive with the path they leave. File edges carry no value, so fan-in on a file input merges branches that never both run. Data edges carry values evaluated on demand; two sources would conflict, so `INPUT_MULTIPLE_EDGES` stays for data inputs ("<node>: data input <label> takes one connection, not <n>").
- **Validation.** `checkPaths` already walks each path with its own flags, so FINISH_ORDER, RENDER_MISSING/TWICE, DAMAGED_ONLY, ELSE_ONLY_NOTIFY and DAMAGED_ONLY_NOTIFY hold per path at a shared node (a damagedOnly node reached from Done on any path is still DAMAGED_ONLY).
- **Engine.** A finish node that both the main path and a gate's `else` (or Render's Damaged) lead into is built once per walk (`Walker.finished`); the branch reuses its actions, so its hook runs and is traced once. A plan-only dry run lists it once in the walk.
- **Editor.** `checkConnection` refuses a second edge only into a data input ("That data input is already connected"); a wired file input still glows while dragging. `onDamagedSide` follows every edge into a finish node's file input and is true only when all of them are on a Damaged side (the validator's per-path DAMAGED_ONLY); `nextNodeRule` follows it. On the job page, `damagedSideOf` leaves out a node the file can also reach without a Damaged output.
