# Decisions: M3: plugins and their security hardening

Part of the decision log: history, not the current rules. Today's rules are in [`docs/dev/`](../dev/); the index of every entry is in [README.md](README.md).

## 2026-10-17 M3 plugins (phase 1)

Built 2026-10-17 on branch `m3-plugins` (core) and `m3-plugins` in `transcoda-plugins`: the plugin SDK 1.0 release candidate, the sandboxed per-plugin process, the installer and catalog client, secrets and the fetch proxy, the engine's plugin finish steps, the API, MCP and Plugins page. Author docs are in [`plugin-sdk.md`](../plugin-sdk.md); the gate record is [`m3-gate.md`](../archive/m3-gate.md). Phase 2 (the six official plugins) and phase 3 (inbound triggers) follow.

### Security promise (binding; do not soften by accident)

- Plugins are trusted code. The sandbox is **accident protection, not a wall**: each plugin runs in its own process under Node's permission model (read only its own bundle, no file writes, no child processes, no native addons, no worker threads, no code generation from strings, an environment of just `PATH` and `NODE_ENV`), and it never touches media or the database; Transcoda does all file work and gives plugins data only. It cannot stop a malicious plugin from using the network freely (raw sockets), signalling same-uid processes (including Transcoda), or exhausting memory the heap limit does not count. The wording the docs and the install dialog carry is in `plugin-sdk.md`, "What the sandbox does and does not do".
- The official catalog only lists builds made by CI from the public source, with a checksum Transcoda verifies before running a line, and a build attestation. Custom catalogs show a warning, and the install dialog says "Built by CI" only for the official one. *(Superseded in part by "M3 security hardening" below: the promise text now also says the plugin user, the signatures and the blocklist, and no longer says a plugin can signal Transcoda's own process in the image.)*
- Install, update, remove, enable, disable, settings, catalogs: admin session only. No token scope, no MCP tool. `list_plugins` is the only plugin MCP tool (read) and an MCP never-list is backed by the API refusing tokens. The REST refusal text is "Plugin management is a UI action".
- Sandbox proof: 17 probes *(19 since the hardening round)* (`SANDBOX_EXPECTATIONS`; the plan's "16" was stale) in `sandbox.test.ts` and, in the image, `--check-plugin … --expect-denials` (exit 1 on a bundle that is not denied, on a probe the table does not know). A Node upgrade that changes an answer fails the suite.

### Architecture

- **One process per plugin**, not one shared host: a crash, timeout or memory kill of one plugin leaves the others' in-flight calls and nodes untouched (tested with a real second plugin). Spawn flags are `--permission`, `--allow-fs-read=<host>`, `--allow-fs-read=<bundle>` (both dropped with `process.permission.drop` after the import), `--disallow-code-generation-from-strings`, `--max-old-space-size`; `env` is `PATH` and `NODE_ENV`; advanced IPC serialization, detached process group, killed as a group.
- **`process.binding` is not deleted** in the host: Node's permission model already answers it with `ERR_ACCESS_DENIED`; deleting it would change the probe to a `TypeError` and say less. fd 4 probe accepts `ENXIO` (kqueue) and `EINVAL` (epoll).
- **Supervisor** checks the bundle's checksum before **every** fork (boot, enable, restart, crash restart); a mismatch is `stopped: bundle changed on disk; reinstall`, no backoff. A node registration failure at boot (a core update took the type) stops the plugin instead of running it half-registered. A first start that fails (install, enable, restart) is `stopped` with no automatic retry; crash restarts back off 1 s doubling to 60 s (reset after 5 min stable) and the plugin stops after 3 crashes in 10 min; failed restart attempts count as crashes.
- **Remove signal:** `remove()` publishes `plugins.changed` with `state: 'disabled'`, `stateReason: 'removed'` rather than a `removed` state (the state enum feeds the contract, the SSE schema and the web; clients refetch on any `plugins.changed` and the plugin is gone from the list).
- **Update** swaps through `startCandidate` and `commit()`; everything that can refuse (node type collisions, duplicates, the `<plugin>:` prefix) is checked before commit; in-flight calls on the old process get the retryable "restarted" rejection. Install with no row for the name first removes `<name>-<version>.*` leftovers of a crash. `install`/`update` refresh the cached catalog once when the version is not in it.
- **Dev plugins** (`TRANSCODA_DEV_PLUGINS`): never persisted, never from a catalog, refused in production. Their settings (and enabled state) live in memory only: a private in-memory table without the foreign key, closed on stop. A dev bundle shadowing an installed plugin, a second bundle of one name, or one that does not start is refused and logged as an error.
- **Bundle path** is `realpath`ed (a symlinked parent such as macOS `/var` otherwise breaks the read grant). `PluginProcess.start` accepts `manifest: null` ("any") for `--check-plugin` and dev bundles.
- **Config:** `TRANSCODA_PLUGIN_CATALOG_URL` replaces the official catalog when set (that is what "official, cannot be removed" means then); `http:`/`file:` catalog urls and `http:` bundle urls are accepted outside production only.
- **Limits** are settings rows `plugins.limits.<key>` (no UI); a malformed or out-of-bound row falls back to the default.
- **Logging:** plugin stdout/stderr lines are forwarded once (as `{ msg: 'plugin log', plugin, level, message, jobId }`, through the same path as `ctx.log`), at most 100 lines/s per process, then dropped with a counter line. Outside production the logger prints `msg key=value …`; production writes the same fields as JSON lines.

### Secrets and the fetch proxy

- **Ruling (fetch-secret tokens).** Nothing secret crosses the process boundary after `init`/`settings`, **except inside a `fetch` message, which the server treats as secret material.** The host replaces each secret occurrence in a fetch input with `__TRANSCODA_SECRET__<fieldPath>__<raw|url|form|b64|b64url>__`; the server's fetch proxy substitutes only **that plugin's own** decrypted secret fields, after the origin check, only into the url, headers and body of that request and its same-origin redirect re-sends, and never into a fetch result, log, problem, trace, finding, API response or MCP answer. A token for an unknown field refuses the request (`secret "<field>" is not a secret field of this integration`, the name cut at 100 characters). Text between tokens still goes through the clear redactor; a request still containing `[redacted]` is refused with a pointer to `auth`.
- **Structured `auth`** on a fetch (`{ basic }`, `{ bearer }`, `{ header }`, `{ query }`) is encoded server-side after substitution, because a prefixed base64 secret (Basic) cannot be tokenised. A `:` in a Basic username is refused; `auth.header` may not name `host`, `content-length`, `transfer-encoding`, `connection`, `proxy-authorization`, `expect` and similar; query auth is appended, not de-duplicated.
- **`test()` with unsaved settings** substitutes from the candidate (merged over stored: a field absent from the candidate falls back to stored) for that call only, through a per-call fetch context (`callId`, `AsyncLocalStorage` in the host, a call map in the process); their secrets stay in the host's bounded redactor set (32, oldest dropped). A fetch from a call that already settled follows the per-process signal and stored policy, and only fetches in flight at settle are aborted.
- **Ambiguous secret names:** two secret fields that sanitise to the same token path (`api-key`, `api_key`), or a path containing `__`, make the plugin `stopped` with the field names, never a value.
- **Known limits (documented in `plugin-sdk.md`):** responses are not scanned for echoed secrets; non-ASCII secrets in header values must use `b64`/`url`/`auth`; a secret used as a header name or JSON key is not protected (only string values are tokenised); secrets shorter than 4 characters are not redacted; overlapping secrets can leave a tail of the shorter one; a plugin's own error text is shown as written (only secrets are redacted).
- **Private addresses are not filtered** (no private-IP or DNS-rebinding filter in the fetch proxy): allowed origins come from admin settings and LAN integrations (Sonarr, Radarr, Jellyfin) need private addresses; the origin allow-list is the control. Redirects are same-origin only (at most 5; 303 and 301/302 on non-GET/HEAD become GET without a body, 307/308 keep it); network errors say only the error code (`request failed: ECONNREFUSED`), never the URL.
- **Fetch limits:** the timeout applies per hop; refusal happens before queueing (no slot, no socket); the token bucket's burst equals the rate and the retry after a 429 takes a token; 429 without a readable `Retry-After` is `rate-limited` at once, `Retry-After` is capped at 60 s (HTTP dates supported); plugin-supplied `host`, `content-length`, `transfer-encoding` and `connection` headers are dropped; non-2xx answers are `ok: true` with the status; the 16 MB body cap also applies to `accept: none`. Before `setPolicy` everything is refused.
- **Settings crypto:** AES-256-GCM with a key derived with HKDF from the instance secret; stored settings hold `{ $enc }` for secret fields only (asserted on the whole table). A secret key with a value that is neither a string nor `{ set: true }` is dropped. `{ set: true }` or an absent secret keeps the stored value; the API never returns a stored secret. No logging in the crypto; errors carry no key, plaintext or ciphertext.
- **Key loss:** losing `secret.key` (or `TRANSCODA_SECRET_KEY`) also loses every plugin's integration secrets (documented in `env.md`). A plugin whose secrets cannot be opened starts with its plain settings only, and the card says `cannot decrypt <plugin>.<field>`.
- **Settings schema changes:** an old key the new schema no longer knows stays stored, encrypted, until the next save drops it; `plugins.settings.get` still answers; `needsReview` is `needs review: <path>: <message>; …` (paths and zod messages only, never values) and the process keeps running. A plugin with no settings row never says needs review. Validation while running uses the plugin's own zod, else the persisted JSON Schema (`z.fromJSONSchema`, without patterns or formats since 2026-10-21); settings schemas are not recursive.
- **Test results:** `lastTest` keeps the failure `kind`, has its message and warnings redacted by value (form plus stored secrets) and cut to 500 characters, and is persisted only when a settings row exists.

### Install, catalog and compatibility

- **Compatibility** everywhere is `semver.satisfies(SDK_VERSION, range, { includePrerelease: true })` (without the option `1.0.0-rc.1` does not satisfy `^1`); `SDK_VERSION` is `1.0.0-rc.1` until the phase-2 gate. `semver` 7.8.5 is the only new dependency (server; the plugins repo takes the same pin for `validRange`).
- **Catalog index:** `{ schema: 1, generated, plugins[{ name, title, description, latest, versions[{ version, sdk, coreTested[], url, manifestUrl, sha256, size, attestation|null, releasedAt }] }] }`; versions and `latest` must be valid semver; entry urls are https (http outside production). Cached on disk for an hour (stale cache served on an error; a 304 refreshes the time); an invalid index with no cache gives an error and no entries; cache write failures are swallowed; the index body is capped at 4 MB. The catalog token goes only over https to `github.com`, `api.github.com`, `raw.githubusercontent.com` and `objects.githubusercontent.com`, decided on the original URL and re-checked on every redirect hop; the installer applies the same rule to bundle and manifest downloads.
- **Installer:** the manifest is fetched and validated before the bundle; bundles are streamed to a `.tmp-*` file, hashed, and refused on a checksum mismatch, a declared size over 32 MB or a body over `min(32 MB, size)`; the manifest is renamed first (a crash leaves an orphan manifest, which `audit` reports and which never loads); targets are checked absent before and right before the rename; names and versions are validated (traversal such as `1.0.0+../../x` is refused; version at most 64 characters); the directory is created 0700 and a symlink or non-directory is refused. One in-process lock per `name@version`.
- **Failure texts:** `checksum mismatch` (plain, no hashes shown); `sdk ^2 is not supported by this server (sdk 1.0.0-rc.1)` (index entry first, then the manifest); `manifest in bundle says <name> <version>, catalog says <version>`; a start failure is `plugin crashed on start: <exit description>`, so a bundle without a plugin default export reads `plugin crashed on start: crashed: bundle has no plugin default export` and nothing is registered. Oversize manifest (over 1 MB) is `manifest`; fetch errors and non-2xx are `network`.
- **Provenance:** `attestation` and `coreTested` are kept in memory from install/update and the last catalog fetch (no column); `updateAvailable` is null until the first `catalog()` call. The catalog output is `{ catalogs[{ catalogUrl, official, error, fetchedAt, plugins }] }` with `installed` (string or null) per plugin.
- **Plugin names** `catalog` and `catalogs` are reserved; node types are `<plugin>:<node>`; a type already provided by core or another plugin is refused at install. The manifest schema is left non-strict (forward compatible).
- **API:** `plugins.list` needs the `read` scope and never includes settings; the other procedures are session only with CSRF. `catalogsAdd`/`catalogsRemove` take a body (DELETE with JSON) and answer the refreshed catalog output from cache; a service `invalid` error maps to `PLUGIN_INSTALL_FAILED` (422 with the reason), `no-integration` to NOT_FOUND, `settings-invalid` to `PLUGIN_SETTINGS_INVALID`, a plugin that is not running to `PLUGIN_NOT_RUNNING` (409). `ready.integration` also carries `id`, `title`, `requires` so the detail is complete.

### Engine

- **Finish phases and `FINISH_ORDER`:** finish nodes run `gate → write → library-manager → media-server → notify`; plugin finish nodes may use only the last three. The order is enforced per path in validation. **Consequence:** a workflow that notifies before the write (the old `core:notify` before `core:replace-original`) is now invalid; an existing one has an active version that cannot run until the notify node is moved after the write. The MCP never-test graphs were reordered accordingly. The error names the node holding the highest phase seen first.
- **`PLUGIN_UNAVAILABLE`:** a plugin node whose plugin is disabled, stopped, restarting or being removed makes the version invalid (`active.runnable` false, `workflows.activate` and `jobs.queue` refuse `WORKFLOW_INVALID`, a queued job fails at start with `workflow invalid: …plugin <name> is not running…`); the node is never treated as unknown. Core and plugin trace entries carry `source`; the web shows a plug icon for `plugin`.
- **Plugin finish steps** run after the write in phase order and never undo it. A failed `required` step is a **problem** (stored in `job_results.problems_json`, listed on the job and in `jobs.stats`, which makes the Jobs page show "needs attention" for a `done` job); an optional one is a warning; `warnings` still also contain the problems (unchanged behavior). A step whose plugin is down is a retryable failure: one retry after `PLUGIN_RETRY_MS` (10 s), then it fails the same way. A stop during the steps ends the job `done` with the problem `the server stopped before the remaining finish actions` (or the cancel variant) and the next start does not re-run the write.
- **Hooks:** `afterReplace` is awaited right after the write (bounded, shutdown- and cancel-aware); `onJobDone`/`onJobFailed` are fire-and-forget after the result row (they must not hold a lane). Hooks are skipped on shutdown and during dry runs, and are not replayed on the next start; `onJobFailed` fires only for failures the pipeline records (not the scheduler's unexpected failure or the startup sweep). Hook contexts carry `dryRun` and `job { id, attempt }`.
- **Prepare can requeue:** a retryable plugin failure on attempt 1 becomes attempt 2 (same rule as the encode); a non-retryable one fails the job with `<nodeId>: <message>`. Remote decide naming an undeclared port throws `plugin N chose port P, which T does not declare`. Finish phase and hook kind are enforced server-side in `remote.ts`.
- **Cancel:** the pipeline's abort signal reaches the plugin as a protocol `cancel` for that call (the host drops its answer and aborts its fetches); a canceled call that still does not answer is killed at its timeout (the process is restarted).
- **Registry:** entries are `{ meta, source, parseSettings, hooks }`; plugin node metadata is persisted so a restarting plugin's nodes are still listed (with `availability`); `listNodes` is cached per registry generation; `workflowsUsingNodeTypes` lists every live workflow (including sub-workflows) whose current or active graph uses the type and does not follow pinned children into parents.
- **Problems columns:** `upsertPluginSettings` keeps the stored `last_test_json`; `updatePlugin` maps patch keys to columns (`integration: null` clears); a sweep-completed job keeps earlier problems.
- **Language names:** `normalizeLanguageValue` treats `xx` as unknown.

### Web

- Plugins page: install dialog states provenance ("Built by CI" for the official catalog, "From a custom catalog" otherwise; an attestation is a link only when it parses as http(s)); installed catalog entries show "installed X" and updates go through the card; remove confirmation names the workflows that use the plugin's nodes and says which versions are active; an untouched stored secret is omitted from the save/test payload; a client-side "Required" check precedes save/test.
- `verdictOf(job)` takes the job; only `done` with problems becomes `attention`; the Jobs page has a needs-attention filter before "Paused".

### Known gaps and findings from the gate (see `m3-gate.md`)

- **A plugin that crashes while a job is in `decide` or `build` no longer fails the job (fixed):** `prepare`, when the workflow is invalid only because a plugin is unavailable, first waits (`PluginRestartGate`, polling the supervisor) while a plugin is `starting` or `restarting`, at most until its next restart plus the start timeout, then validates again; a plugin that is `stopped` (gave up), disabled or removed is not waited for and fails the job at once with `PLUGIN_UNAVAILABLE`. A call to a starting or restarting plugin is now a retryable `PluginCallError`. Still down after the wait: requeued once as attempt 2, failed at the last attempt (attempt counting unchanged). Validation is not relaxed (review focus 4). Tested with the real host fixture (kill -9 by `PluginService.pid` during decide: the job ends `done`, attempt 2).
- **Installer and catalog downloads no longer use the global `fetch` (fixed):** the Node 24.21 undici crash (`assert(!this.paused)`, HTTP/1.0 close-delimited host plus a slow reader) is avoided by `plugins/http-get.ts`, a `fetch`-shaped GET on `node:http(s)` (manual redirects, so the GitHub-token host re-check in `fetchGuarded` is unchanged; streamed bodies, size caps and timeouts stay with the callers). A malformed or HTTP/1.0 server is an ordinary `network` failure (tested against a raw TCP HTTP/1.0 server and a garbage answer). The installer removes its `.tmp-*` files on every failure path, and the startup audit removes stale `.tmp-*` files from `/config/plugins` (reported as removed).
- Not a defect but worth knowing: the image-level sandbox job runs after the image push (a failure is a red workflow on a published tag, accepted for now); `@transcoda/sdk` is not published, so the plugins repo links it from a core checkout (`CORE_REPO_TOKEN` in CI while the repo is private); the plugins repo's example test still patches `now` onto `fakeHookContext()` (the SDK now supplies it).

## 2026-10-17 M3 security hardening

Built 2026-10-17 on `m3-plugins` (core) and `m3-plugins` (plugins repo) from the sandbox architecture review's findings H1 (plugin hosts shared the server's uid), H2 (nothing hardened the container), M1/M2 and the blocklist idea, before phase 2. The owner approved the review's recommendations the same day ("go with recs"). What a plugin can and cannot do now is in [`plugin-sdk.md`](../plugin-sdk.md) ("What the sandbox does and does not do"), the variables in [`env.md`](../env.md), and the signing and blocklist workflow in the plugins repo's README. The security promise text is shared verbatim by `plugin-sdk.md` and `SECURITY_PROMISE` in `apps/web/src/plugins/pluginText.ts`; `pluginText.test.ts` pins the two equal (and `CUSTOM_CATALOG_WARNING`).

### Rulings from the owner (2026-10-17, "go with recs")

1. Plugin user `65001:65001`; the entrypoint `chmod o-rwx` of `/config` and `/transcode` (persists on the host bind mounts; accepted). Works with `PUID=0` (the owner's server setup; a uid-0 server plus a setpriv host was tested).
2. No `useradd`/`groupadd` (numeric ids everywhere; read-only rootfs). `docker exec … whoami` prints `unknown uid` (the measured text is `whoami: cannot find name for user ID <id>`); `os.userInfo()` throws for such a uid (nothing in Transcoda calls it; `HOME` is exported).
3. The blocklist lives on the plugins repo's `catalog` branch beside `index.json` (same key, same CI, one secret).
4. A plugin installed from a signed custom catalog that is later removed stops at its next start with `signed with an unknown key <id>` (verified against an empty key list, never skipped).
5. `pids_limit: 1024` in the repo compose; `mem_limit` stays commented there with the formula, and is set to `mem_limit: 3g` in the deploy plan's compose for the owner's server.
6. Dev-mode plugins (`TRANSCODA_DEV_PLUGINS`) are **not isolated**: they run as the server's user, documented; refused in production anyway.
7. The owner generates the production signing key later; until the public key is pinned, a production build refuses the official catalog (`catalog signature missing` / `signed with an unknown key`) and logs one warning at start. Local and dev flows use `TRANSCODA_PLUGIN_CATALOG_KEY=none` or `dev:<hex>`.

Controller rulings during the round (also "go with recs"): `TRANSCODA_PLUGIN_CATALOG_KEY=<id>:<hex>` may replace the pinned set in production (whoever sets the environment controls the server); a custom catalog's key is entered by the admin as `<keyId>:<hex>[,…]`, the same format (the first draft hard-coded the key id `custom`); production on Linux without isolation refuses to start unless `TRANSCODA_PLUGIN_ISOLATION=off`.

### Plugin user and container

- **Mechanism: ambient capabilities on the server plus `setpriv` per host.** The entrypoint runs as root only to prepare ids and directories, then execs the server as `PUID:PGID` through `setpriv` with `CAP_SETUID`, `CAP_SETGID` and `CAP_KILL` as bounding, inheritable and ambient capabilities (`00000000000000e0`, effective too) and no-new-privileges; the server starts each host as `PLUGIN_UID:PLUGIN_GID` through `setpriv --reuid --regid --clear-groups --inh-caps=-all --ambient-caps=-all --no-new-privs`. Rejected: (a) a root launcher process that forks hosts on request (an IPC relay for every host message, and a root Node process alive for the container's life); (b) a setuid helper (defeated by `no-new-privileges`, which we want); (c) user namespaces (`unshare(CLONE_NEWUSER)` is blocked by Docker's default seccomp profile without `CAP_SYS_ADMIN`). The cost of the chosen one: the server could `setuid(0)` inside the container; that root has no capabilities (bounding set) and a read-only rootfs, so it is "a user that owns root's files", and the server already holds every secret the container has.
- **`CAP_KILL`** because `kill(2)` across uids needs it: the supervisor SIGKILLs a spinning host and its process group.
- **`CAP_FSETID` for the entrypoint only** (compose `cap_add` has it; the server's bounding set drops it): `chmod 2710` on a directory whose group the caller is not in silently loses the setgid bit without it (measured in the preflight), and staged bundles would then be `644 PUID:PGID`, unreadable for the plugin user.
- **No `--bounding-set` on hosts.** Dropping bounding-set capabilities needs `CAP_SETPCAP` in the effective set, which the server deliberately lacks: with util-linux 2.41.5 (the preflight) a host spawned with `--bounding-set=-all` does not start (`setpriv: apply bounding set: Operation not permitted`); with the image's 2.38.1 the flag happened to be a silent no-op. Either way the host argv never carries it. A host's `CapBnd` stays `e0`; with zero permitted, effective, inheritable and ambient capabilities and `NoNewPrivs 1` it cannot be exercised, so it is harmless. The identity check and the image CI never look at `CapBnd`.
- **Engine children are wrapped too (deviation from the plan).** The plan accepted that ffmpeg and ffprobe inherit the server's three ambient capabilities as "not a regression". The review of Task 7 asked for more and `engine/child-caps.ts` now starts every ffmpeg and ffprobe through `setpriv --inh-caps=-all --ambient-caps=-all --no-new-privs --` when isolation is configured (a missing ffmpeg then shows as setpriv's non-zero exit rather than `ENOENT`; transcoding is unavailable either way). The image CI's hardening job proves such a child has zero capability sets.
- **No `useradd`/`groupadd`:** `setpriv --reuid/--regid/--groups` take numbers; a passwd entry was cosmetic and wrote `/etc/passwd` and `/etc/group`, which a read-only rootfs forbids. `HOME` is exported (`/config`). Consequences: `whoami` fails with `cannot find name for user ID <id>`, `os.userInfo()` throws (nothing in `main.js` or `plugin-host.js` calls it), and a `PUID` change no longer needs a recreated container (it applies on restart; `TRANSCODA_CHOWN_CONFIG=1` re-owns existing files once). The entrypoint validates `PUID`, `PGID`, `PLUGIN_UID` and `PLUGIN_GID` as plain decimals up to 2147483647 and the plugin ids as at least 1 (4294967295 is setpriv's "leave unchanged" sentinel and must never reach it; 0 would give a host that regains capabilities), `PLUGIN_UID`/`PLUGIN_GID` must differ from `PUID`/`PGID`, and `PLUGIN_GID` must not be a passed-in device group; all exit 2 with the offending name.
- **`chmod o-rwx` on `/config` and `/transcode`:** the plugin user must not reach the database, `secret.key` or the manifests. On a typical `755` volume the result is `750` (group bits stay; "no other bits" is the rule, not `700`). On a host bind mount the change persists. Docker Desktop for macOS (virtiofs) does not enforce it: the check passes only on Linux or with a named volume. Bind-mounted media (`/data`) is the user's and is not touched; there Node's permission model is the wall.
- **The staging copy, and why not `/config/plugins` group-readable.** A host needs to read its bundle, but giving the plugin group traversal on `/config` would expose every `0644` file under it. Instead the server writes the verified bytes to `/run/transcoda/plugins/<name>-<version>.js` (tmpfs; directory `PUID:PLUGIN_GID`, mode `2710`; file `0640`, exclusive temporary file then rename, real path used for the sandbox read grant) before every start, and clears the directory at start. An update stages the **candidate** and verifies it before the commit; the old version's copy goes after the commit; a disabled plugin updated in place loses its staged copy at once and stages again on enable; install rollback, discard, disable and remove unstage. A staging failure is `stopped: cannot stage bundle: <reason>`, no restart loop.
- **Identity check after spawn.** Once the host reports ready, the supervisor reads `/proc/<pid>/status` and stops the plugin (`plugin host is not isolated: <field> expected <x>, got <y>`, no restart) when the real uid or gid differs, any of the effective, permitted or ambient capability sets is not zero, or `NoNewPrivs` is not 1; an unreadable identity fails closed. It runs after the host evaluated the bundle's module code (so it proves the steady state, not the first lines); it reads the real uid and gid only. `--check-plugin` reports the same fields (`isolation`) and the image CI asserts them. Known small gap: the `--check-plugin` command does not compare the host's gid with the server's own gid when parsing its isolation.
- **`--user`, an unpreparable staging directory and the "same-uid with a log line" idea.** The plan's first draft let a container started with `--user`, or a staging directory that could not be created, quietly fall back to same-uid hosts. That is not what shipped. The entrypoint then exports no plugin variables and logs `plugin isolation is off`; the server, in production on Linux, **refuses to start** unless `TRANSCODA_PLUGIN_ISOLATION=off` (controller ruling), and with it logs `plugin hosts run as the server's user`. Outside production same-uid runs without a requirement. **What same-uid means precisely** (final review): the plugin host runs as the server's uid and group, with no capabilities. When isolation is off, whether by `--user`, an unpreparable `/run/transcoda`, or `TRANSCODA_PLUGIN_ISOLATION=off`, the entrypoint (if root) execs the server with `--inh-caps=-all --ambient-caps=-all --bounding-set=-all --no-new-privs` (the server needs `CAP_SETUID`/`CAP_SETGID`/`CAP_KILL` only to start a plugin user), and, as a second line, the server wraps plugin hosts and ffmpeg/ffprobe in `setpriv --inh-caps=-all --ambient-caps=-all --no-new-privs --` whenever it is Linux, `setpriv` exists and `/proc/self/status` shows a nonzero `CapAmb`. `entrypoint.test.sh` checks both off paths and CI runs it. `TRANSCODA_PLUGIN_ISOLATION=off` is honored by the entrypoint (final review: it exports no plugin user and starts the server without capabilities); the server itself reads it only when no plugin user is configured, so a server run directly with a plugin user ignores it. Configured isolation that cannot work is a startup error, never same-uid: `TRANSCODA_PLUGIN_UID` equal to the server's uid or `TRANSCODA_PLUGIN_GID` to its gid, set on a non-Linux platform, set without `TRANSCODA_PLUGIN_GID`, outside 1..2147483647, or set while the server lacks `CAP_SETUID`/`CAP_SETGID`/`CAP_KILL` (read from `/proc/self/status`), without an executable `setpriv`, or with a staging directory that is not writable (`IsolationError`, exit 2).
- **Dev plugins are not isolated** (ruling 6): `isolated: false`, they run from their own path as the server's user and are never staged; `TRANSCODA_DEV_PLUGINS` is refused in production.
- **Cross-plugin isolation is uid-level only.** All hosts share `PLUGIN_UID:PLUGIN_GID`: a plugin can signal a sibling host and, through the shared group, read the staged bundles at the operating-system level (bundles are public code; the permission model's read grant is what separates them). Per-plugin uids were not worth the id management; per-plugin network and process namespaces mean the separate-container design below.
- **Two facts measured in the preflight** that shaped the code: setpriv orders its operations itself, so the entrypoint's option order does not matter (the line gives the server exactly `e0`/`NoNewPrivs 1`, also with `PUID=0`); and `spawn(setpriv, …, { stdio: [..., 'ipc'], serialization: 'advanced', detached: true })` carries the IPC channel (the child's pid is setpriv's, which execs node, so the pid and `kill(-pid)` keep working).
- **Compose and CI.** `docker/docker-compose.yml`: `security_opt: no-new-privileges:true`, `cap_drop: [ALL]`, `cap_add: [CHOWN, DAC_OVERRIDE, FOWNER, FSETID, SETUID, SETGID, SETPCAP, KILL]`, `read_only: true`, tmpfs `/tmp` and `/run/transcoda` (`mode=0755`, 256 MB), `pids_limit: 1024`, `mem_limit` commented with the formula (set to 3g in the deploy plan's compose for the owner's server), and a comment never to use `privileged`, `seccomp=unconfined` or `docker.sock`. Two image CI jobs: `sandbox` (per architecture, the compose flags, asserts `probes == 19`, uid `65001`, all capability sets zero, `NoNewPrivs 1`) and `hardening` (`docker/entrypoint.test.sh` in the base image with the real `setpriv`, then the shipped compose file against the pushed image: the server's five capability lines are exactly `e0` with `NoNewPrivs 1`, the plugin user cannot signal the server nor list `/config`, the root filesystem is read-only, ffmpeg works, no isolation warning in the log, a server child has no capabilities). Neither job has run on GitHub yet.

### Signing and the catalog

- **Format.** A detached file beside the document, `<url>.sig`: `{ "schema": 1, "alg": "ed25519", "keyId": "<id>", "signature": "<base64 of the 64-byte signature over the exact bytes of the signed file>" }`, strict (no extra keys, canonical base64, `keyId` matches `/^[A-Za-z0-9._-]{1,64}$/`, at most 16 KB). Public keys are the raw 32 bytes as 64 lowercase hex characters; the private key is PKCS8 PEM. `node:crypto` only, no new dependency in either repo. The signature covers the bytes, not the checksum: the installer reads the stored bundle back and verifies it, and the catalog and blocklist caches keep the exact verified bytes and their `.sig`.
- **Keys are pinned in `apps/server/src/plugins/official-keys.ts`** (`OFFICIAL_SIGNING_KEYS`, empty until the owner generates the production key). One key signs bundles, the index and the blocklist. `TRANSCODA_PLUGIN_CATALOG_KEY` replaces the list (also in production, see the rulings); `none` is refused when `NODE_ENV=production`; an empty list means official installs are refused (`catalog signature missing` or `signed with an unknown key <id>`), with one warning at start. A whitespace-only value counts as unset. A self-hosted catalog in the official slot is verified with the pinned keys.
- **Missing is never "unsigned".** A catalog whose index loads but whose `.sig` answers 404 is `catalog signature missing`; a 5xx on the `.sig` is a fetch error (the last verified cache may serve); a signature disagreement is retried once past the CDN cache (`raw.githubusercontent.com` caches the document and its `.sig` separately), then falls back to the last verified index only; a missing, malformed or unknown-key signature never falls back. A signed plugin whose `.js.sig` was deleted is `bundle signature missing; reinstall` before the start, never started on the checksum alone; a changed one `bundle signature invalid; reinstall`; a removed key `signed with an unknown key <id>; update the plugin`. An install records `signed_by` (migration 0007, plus `signing_keys` on `plugin_catalogs`).
- **Custom catalogs pin a key when they are added**: `<keyId>:<hex>[,…]` in the same format (ruling above; the signature files must name one of those ids), refused on the official url (`the official catalog's key is set by TRANSCODA_PLUGIN_CATALOG_KEY`) and on a url with a query string. Re-adding a known url without a key keeps the pin (`COALESCE`); to unpin, remove the catalog and add it again. Stored keys that no longer parse verify nothing (never "unsigned"). Removing a signed catalog makes its plugins stop at their next start with `signed with an unknown key <id>` (ruling 4: verified against an empty key list, never skipped).
- **Installs recorded unsigned are never checked later.** A plugin installed from an unsigned catalog or with `none` has `signed_by` null and is not signature-checked at any later start, even after a key is pinned or the catalog gets signed; reinstall it. After switching a signed install to `none`, the start fails with the unknown-key message and its `; update the plugin` hint, which is then misleading.
- **No freshness.** Signed documents carry no expiry: a validly signed older index can be replayed to someone who controls the network path, hiding an update or offering an older signed build. *(Partly superseded 2026-10-21: a verified index older than the cached verified one is now refused, see "Signed catalog index is monotonic". A server with no cache, or after the cache is cleared, still accepts any validly signed index.)* The blocklist has this protection (below).
- **Rotation.** Add the new public key to `official-keys.ts` and release core; then switch the CI secret; remove the old key two core releases later (a bundle signed with a removed key then stops at its next start with `signed with an unknown key <id>`). **Compromise runbook, in this order** (final review; the first draft said "remove the key now and blocklist", which cannot work because the blocklist is signed with the same key): (1) generate a new key; (2) pin it and drop the compromised one in a core release; (3) re-sign the index and the blocklist with the new key; (4) only then add the sha256 entries for the affected bundles. A server on an older core has no protection until it updates: it still trusts the compromised key and cannot verify the new blocklist. The plugins repo README part is a separate change.
- **A custom `TRANSCODA_PLUGIN_CATALOG_KEY` makes the official blocklist inert.** The blocklist is verified with the same keys as the catalog, so overriding them in the official slot leaves the official blocklist unverifiable. The server logs one warning at start (`the official plugin blocklist is configured but TRANSCODA_PLUGIN_CATALOG_KEY replaces the official signing keys: the blocklist is inert and blocks nothing`) when the blocklist url is the official one and the keys differ from `OFFICIAL_SIGNING_KEYS`.
- **Production signing key and CI secrets are the owner's hand-off:** generate with `node scripts/sign.mjs keygen --out <dir>`, store the PEM as `PLUGIN_SIGNING_KEY` and the id as `PLUGIN_SIGNING_KEY_ID`, pin the printed public key, and (later, noted in the controller ledger) put the secret in a GitHub Environment restricted to `main` and the release tags with required reviewers and pin the actions by SHA.

### Blocklist

- **Location.** `blocklist.json` and `blocklist.json.sig` on the plugins repo's `catalog` branch beside `index.json` (ruling 3: same key, same CI, one secret; a second repository would add a secret and a workflow for no isolation gain, since whoever controls the signing key controls both anyway). The hand-edited source is `catalog/blocklist.json` on `main`; `catalog.yml` validates it with `scripts/check-blocklist.mjs`, stamps `generated`, signs and pushes it, even when the index build fails.
- **Semantics (from the review): fail-open on a fetch error, fail-closed on a positive match.** Checked at install and update, and before every start; an installed match is stopped with `blocklisted: <reason>` (disabled plugins stay disabled and are refused at their next start). Entries match by `sha256`, or by `name` with an optional semver `versions` range (`versions` needs `name`); an entry with both `sha256` and `name` matches **either** (OR), so a name-and-range entry with a sha256 also blocks a renamed copy of that exact build and blocks every build of that name in the range, not only the hashed one; `reason` is 1-200 characters, `url` an optional https advisory link. One malformed entry makes the whole document invalid: it is reported as a fetch problem and the previously cached list keeps being enforced. `generated` is monotonic: an older signed list never replaces a newer one, so replaying an old document cannot lift a block. A list that cannot be read blocks nothing.
- **Core mirrors the plugins repo's schema** (strict objects, non-blank range, trimmed reason). The two content checks `check-blocklist.mjs` adds (unique ids, `added` not after `generated`) stay CI-only in core: a list that is merely untidy must still be enforced. A follow-up for the plugins repo: warn when a `versions` range normalizes to `*`.
- **Timing and cache.** Fetched at start in the background (3 s timeout, nothing waits for the network; the cached list, verified again, is in force before any plugin boots), then hourly, and when a catalog refresh is asked for (`catalog(refresh=true)` runs the full recheck, so a running plugin newly listed is stopped at once, not at the next hourly recheck); cached at `<config>/plugins/.catalog/blocklist.json` with its ETag and `.sig` (a 304 only answers for a cache that still verifies). A dev plugin is never blocklisted. The blocklist uses the official keys, so it is inert until a production key is pinned (hand-off).
- **Where it shows:** the plugin card (`Blocklisted: <reason>`, with an advisory link for http(s) urls), the catalog and install dialog (`blocklisted: <reason>`, install disabled), `list_plugins` (`BLOCKLISTED: <reason>`), the catalog output's `blocklist` status, and `plugins.list`'s `blocked`.

### Known, documented, not fixable in-process

- **`--disallow-code-generation-from-strings` is not a boundary** (the M2 sandbox review): `vm.runInNewContext` and `vm.compileFunction` run strings regardless. No privilege is gained (the permission model and the plugin user still apply); documented as "do not rely on the flag".
- **Raw sockets (H3).** The network is outside Node's permission model and the fetch proxy has no private-address filter: a plugin can reach the LAN, the server's own API on `127.0.0.1` and anything else the container can reach. Hence never mount `docker.sock`. Documented in the promise and in `plugin-sdk.md`.
- Memory outside the V8 heap is caught only by the 1 s RSS poll and the container limit.

### What stays open

- A per-plugin network namespace needs plugins in a separate container (the design alternative); not done.
- The attestation link in the install dialog is only a link: server-side verification of build attestations is phase 2's item.
- A GitHub Actions run of the new image jobs, and the checks on the owner's server (cgroup memory limit, NVENC under `cap_drop: ALL`), are still to be done (Task 11).
