# Decisions: November 2026

Part of the decision log: history, not the current rules. Today's rules are in [`docs/dev/`](../dev/); the index of every entry is in [README.md](README.md).

## 2026-11-02 Never re-run a processed file

- **The rule (the owner).** A workflow never runs a file again on its own once any of its versions processed it: `done`, `nothing_to_do` or `kept_original`, as the job's source or as the file it wrote. This holds for Scan now and queueing a folder (`queueRun`) and for a job re-pinned to a newer version when it starts, as it already did for the automatic library check. Process again (`force`) overrides it.
- **Exceptions.** A `failed` result counts only for its own version, so a newer version still tries a file an older one failed on. A dry run is a preview a person asked for: it keeps the check for its own version only (`findPriorRun(..., { sameVersion: true })`). Dry-run results never count.
- **Reason.** `already <outcome> by v<N> on <ISO time>`, then "this file is the original from before then (moved back from the recycle folder?)" for a `done` source match or "this file is what that job wrote" for an output match, always ending "use Process again to run it anyway". The web formats the time.

## 2026-11-02 Restore original

- **What it does (#39).** `recycle.restore` takes a recycle entry's path. An `original` entry is restored: the job's output moves to the recycle folder (first free `recyclePathFor` name, a `restored-output` entry pointing at the restore), the original moves back to the job's path, and the job's recycled subtitle files (`sidecar` entries) go back to their recorded paths. A `restored-output` entry undoes that restore the same way in reverse. A `sidecar` entry is refused: it comes back with its video.
- **Checks before anything moves.** The job is `done`, recycled its original (`replacedTo: 'recycle'`) and has no replace or restore journal; no queued or running job works on the same path; the library, the job's folder and the entry's folder can be reached; the file at the job's path is still the output (`output_fingerprint`; undo: still the original, the result's `fingerprint`); the recycled copy is there with its recorded size (a copy removed by hand drops its row). A refusal moves nothing and says why (`RECYCLE_REFUSED { reason }`, 409).
- **One operation, journaled.** The restore journal (`jobs.restore_journal`) is claimed before the disk checks, so a second restore of the same job is refused while one is under way. Each move is `renameNoClobber` (never over an existing file), journaled before it runs (`next`). A failed move rolls back the moves before it from what is on disk; the start-up sweep does the same for a restore a crash cut short and leaves the job `done`. A move it can't undo (another file in the way) is a conflict, logged, and keeps the journal. The database records (`restores` row, `recycled` rows) are written in one transaction after the last move.
- **Subtitle files.** One whose recycled copy is gone, whose path is taken or whose path wasn't recorded stays where it is; the restore goes ahead and names it ("not brought back: …").
- **Afterwards.** A restored file is the job's source again (same inode and mtime), so the never-re-run rule makes it `already_processed` for every version until Process again. Space saved leaves out a job whose restore is in effect and counts it again after an undo. The job page shows "Original kept until <date>" (`recycledAt` + retention days) and, after a restore, "Original restored on <date> by <user>".
- **Who.** A person's session only (`requireHumanSessionWith('Restore is a UI action')`), like Process again: no token scope and no MCP tool, since it moves files in the library.

## 2026-11-02 Recycle folder page

- **Where (#41).** A "Recycle folder" item in the main menu after Libraries (`/recycle`, icon `trash`). One library at a time, picked in a switcher showing each library's file count; without `?library=`, the first library whose folder holds anything (else the first). It shows the folder, its size, the free space on that disk, and the retention note with a link to Settings → Recycle folder.
- **Rows.** One per `recycled` entry: where it came from in the library, size, its job, when it was recycled, and "Deleted on <date>" (recycled time + retention days; the free-space cap may delete it sooner). A subtitle file sits under its video's original and has no actions of its own (it comes back with it); one without that original is its own row. A restore's set-aside output is labeled "Transcoda's version (restored original)" and its Restore puts it back (the undo). A phone shows a card per row.
- **Delete and Empty folder.** Both permanent, both confirmed (Empty states the count and size). They remove files only through `removeRecycledRow`, the code retention uses, so an entry whose job has a replace or restore journal is never removed: Delete refuses it, Empty skips and counts it. Empty sends the newest `recycledAt` the page listed, so a file recycled after the person looked stays.
- **API.** `recycle.list` (`read` scope: tokens may look), `recycle.delete` and `recycle.empty` (a person's session only, "Deleting from the recycle folder is a UI action"). An unknown library is NOT_FOUND.
- **Job page.** A restored job's line links to its library's Recycle folder page, where the undo is.

## 2026-11-09 SI units everywhere

- **Decision: every size a person reads or types is SI** (1 kB = 1000 B, 1 MB = 10^6 B, 1 GB = 10^9 B), printed by one formatter, `fmtBytes` in `@transcoda/shared` (three significant digits, "kB"), which the web's `lib/bytes.ts` re-exports and the server's reasons and messages use too. Binary units stay only in internal byte math that never reaches a person (`/proc` kB, Node's heap flag, buffer sizes).
- **Minimum free space.** New `TRANSCODA_HEALTH_MIN_FREE_GB` (default 5). The older `TRANSCODA_HEALTH_MIN_FREE_GIB` is still read when the GB variable is unset, so a setup that set it keeps the same margin to the byte; GB wins when both are set. Config holds the margin in bytes (`healthMinFreeBytes`, rounded to whole bytes) plus the variable in effect; the settings contract's `queue.minFreeGib` became `queue.minFreeBytes` (bytes, the variable in effect), and Settings prints it with `fmtBytes`. The floor and the default are 5 GB (were 5 GiB, about 5.37 GB): a round number in the unit people read, and 7% less margin is still far above any filesystem's needs.
- **Same change elsewhere.** The replace's free-space margin (`FREE_SPACE_MARGIN_BYTES`) is 5 GB; `TRANSCODA_DECODE_MEMORY_GIB` is now `TRANSCODA_DECODE_MEMORY_GB`; the GiB variable is still read when the GB one is unset (like the minimum free space), since 0.4.0 may ship it first; its default bounds 1 GB and 4 GB; the sidecar cap is 8 MB; File matches' MB settings are 10^6 bytes (supersedes "MB means MiB" above: a stored 500 now means 500,000,000 bytes); the request body limit is 2 MB, as the editor's message already said; plugin settings migrations are capped at 256 kB. The space-wait reason now reads "waiting for 5.40 GB free on … (5.10 GB free)".
- **Left binary on purpose:** plugin `rssMb`/`heapMb` limits (Node's `--max-old-space-size` is MiB; the reported RSS in a kill reason is SI MB), the job-log tail (65,536 bytes) and the plugin icon cap (16,384 characters), whose docs now give the exact count instead of a binary unit.

## 2026-11-11 Metrics for Prometheus and Home Assistant

- **Why.** People want Transcoda in Grafana next to the rest of their server, and in Home Assistant. The SQLite schema is not a stable interface, so the server serves the numbers itself (issue #89).
- **Auth: a new exact scope `metrics`** (or a session). It gives nothing else (no REST read, no MCP tool) and no other scope includes it, so a token sitting in `prometheus.yml` or Home Assistant reads counts only; a `read` token lists paths and logs, too much for a scrape config. On by default, since nothing is readable without such a token; `TRANSCODA_METRICS=false` answers `404` before auth. `/metrics` is under the host check like `/api`. Rejected: off by default behind an env var (a restart plus a token for the same result), reusing `read`, and a separate listen address (a second server and port mapping, and still needs auth once exposed). An older server drops the unknown scope on read (`clean()`), so a downgrade only makes those tokens useless; no migration.
- **Hand-written exposition**, no `prom-client`: a typed catalog (`metrics/catalog.ts`) and a ~70-line renderer. Avoids a dependency with a global registry and default process metrics. A strict parser (`metrics/parse-exposition.ts`, tests only) reads the output back.
- **One snapshot for both endpoints**, cached 5 s (shared in-flight like deep health), from a few aggregate queries (`db/repos/metrics.ts`) plus in-memory state: queue paused, the GPU sampler's last reading, `statfs` of the transcode folder, and a `MetricsRecorder` fed by a new synchronous `EngineEvents.listen` (no buffer, so no `resync` gaps) for job durations and encode-slot busy time.
- **Cardinality.** Labels only from small sets: library name, state, outcome, lane, encode slot id, GPU id. No path, job id, file or failure text: a failure reason is free text, so "failures by reason" waits for a reason code (now `transcoda_jobs_failed`, see 2026-11-17). Two live libraries with the same name get an 8-character id prefix so their series do not collide; deleted libraries drop out; a rename starts new series.
- **Database totals are gauges.** Saved bytes go down when an original is restored, and a retry deletes a result row, so they are not counters; the dashboard charts them with `delta()`. Saved bytes follow the Jobs page rules (only `done`, restored ones left out). Only in-memory values are counters/histograms, reset at restart.
- **Status JSON** (`system.status`, `GET /api/v1/system/status`, in the contract and OpenAPI): the same snapshot summed up, for Home Assistant's RESTful sensor, which cannot read the Prometheus format.
- **Dashboard kept in sync by tests** (`metrics/sync.test.ts`): every `transcoda_*` name in a panel or variable query must be in the catalog, panels use the `${DS_PROMETHEUS}` import input, ids are unique, and `docs/metrics.md` lists every metric with its type and labels in catalog order.

## 2026-11-11 Plugin hosts before install (#100, SDK 1.3.0)

- **Derived, not declared.** The manifest's new `network` comes from the integration's `allowedOrigins` (`pluginNetwork` in the SDK): `{ origin }` for a fixed origin, `{ setting, label }` for `'$settings.<field>'`, the label being the setting's description up to its first comma, else the key; `[]` without an integration. Authors write nothing, and the list cannot drift from what the fetch proxy enforces. Rejected: a separate hand-written `hosts` field (a second list that can disagree with the enforced one).
- **No wildcards.** `allowedOrigins` has none and the proxy pins exact origins; a host the user chooses comes from a url setting.
- **What the dialog promises.** "Connects to", then: "Transcoda's HTTP client lets this plugin reach only what is listed here. It can't stop a plugin that opens its own connections." This matches the security promise (raw sockets are outside Node's permission model). `[]` reads "Nothing: it makes no network requests through Transcoda"; a build from before 1.3.0 reads "Not listed: this build predates host lists." (no warning tone).
- **Trust chain.** The catalog index carries `network` per version (optional). The installer refuses a manifest whose `network` differs from its catalog entry (`the manifest lists other network hosts than the catalog entry`); the start check compares the bundle's own derived list with the manifest's (`…differs from the catalog entry in: network`). Both checks apply only when the catalog side carries the list, so older manifests and indexes keep installing. The contract's catalog version has `network: … | null` (null: not listed). `--check-plugin` prints it too.
- **Updates.** The update dialog lists the target version's hosts and marks each one the installed version's list lacks ("new", plus a note the dialog is described by); a setting counts by its key, not its label; nothing is marked when either list is unknown. An update that adds a host always opens the dialog, also the one-click Update, and Update all skips it and names it ("needs a look: it connects to a new host"). Both lists come from the catalog entry, so a plugin installed from a catalog that no longer lists its version is not compared. The installed plugin's card does not show hosts yet (follow-up).
- **Release order.** Any order is safe (optional field; an old core's zod strips the unknown key), but the natural one is: core with SDK 1.3.0, then the plugins repository (its bundle-manifest script derives the same list, the catalog builder copies it, official plugins take patch releases), then the catalog rebuild.

## 2026-11-17 Failure codes

- **Why.** "Failures by reason" was left out of the metrics because a job's `reason` is free text (paths, ffmpeg lines). A failed job now also records a code, `jobs.failure_code` (migration 0018), from a fixed list in `@transcoda/shared` (`FAILURE_CODES`): `interrupted`, `source_unreadable`, `source_changed`, `encode`, `verify`, `replace`, `workflow`, `internal`. The UI and the API keep showing the sentence; the code is for metrics only (not in the contract yet).
- **Where it is set.** Every write of `failed` names a code: the pipeline's `Failure` (built by `final(code, …)`/`retryable(code, …)`) and its `finish`, whose `failed` overload requires one; the startup sweep (`interrupted` for a second interruption and a rolled-back replace, `replace` for the other recovery outcomes); the scheduler's `failUnexpected` (`internal`). A replace that settles in the pipeline is rewritten by the pipeline's own failure (`replace`, or `source_changed` when the file changed or moved). Walk failures are `workflow`, plugin errors included. Any other final state clears the code, and so does Retry failed (as it clears `reason`).
- **Metric.** `transcoda_jobs_failed{library, reason}`: a gauge from the database like `transcoda_jobs_finished` (a retry takes a failure out again), `reason` = the code or `unknown` for rows from before 0018 (`COALESCE`; old rows are not guessed from their text). Cardinality is bounded: 9 values × live libraries, only non-zero combinations listed.

## 2026-11-17 Node 26

- **Why.** Node 26 is the active LTS line since late October 2026 and Node 24 is in maintenance. The 2026-10-26 entry left the move for a separate change with a sandbox re-check; this is it.
- **What moved (together, as the Node.js Renovate group expects).** `.node-version` 26.13.1; root `engines` `>=26.13.1`; `ARG NODE_IMAGE=node:26.13.1-bookworm-slim@sha256:5df79989…b0f1` (multi-arch index); tsdown `target: 'node26'` for the server, the plugin host, the test-harness bundles and the SDK (tsdown 0.23.7 takes it without a warning); `@types/node` 26.6.6. Renovate still leaves Node majors to a person.
- **SDK.** `@transcoda/sdk` `engines` is now `>=26` (no known users yet). It takes effect with the next SDK publish.
- **`process.permission.drop` is typed now.** `@types/node` 26 declares it, so the plugin host's own interface and the double cast are gone.
- **corepack is no longer in Node.** Node 26 (and its images) ship no corepack and no yarn; npm 11 stays. The image's build and deps stages install `corepack@0.36.0` from npm (`ARG COREPACK_VERSION`, kept current by a Renovate regex manager), then `corepack enable` as before, so `packageManager` stays the one pnpm pin. The runtime stage deletes npm as before. README and CONTRIBUTING say `npm install -g corepack` first. CI is unaffected (pnpm/action-setup).
- **Sandbox, checked under 26.13.1.** The denial table (`sandbox-expectations.ts`) is unchanged: the built image's `--check-plugin … --expect-denials` reports ok, 19 probes, uid 65001, no capabilities, NoNewPrivs 1. New in 26: `--permission` also covers the network. Without `--allow-net` (the host never passes it), TCP connect, listen, UDP send, DNS lookups and the global `fetch` all fail with `ERR_ACCESS_DENIED`; Node 24 allowed all of them under the same flags. The fetch proxy is unaffected (it goes over the IPC pipe) and the official plugins only use `ctx.fetch`. `--allow-inspector --inspect` (dev only) still serves the inspector. Not yet relied on: there is no denial probe for it, and the docs and the install dialog still say Transcoda cannot block a plugin's own connections (follow-up: add a probe, then reword).
- **Verified.** Under `node:26.13.1-bookworm-slim` (Node 26.13.1, ABI 147, pnpm 12.20.0 through corepack 0.36.0): `pnpm install --frozen-lockfile`, `pnpm check` (typecheck, Biome, check-deps, check-licences, Vitest: 347 files and 5135 tests passed, 55 skipped: the real-ffmpeg suites, which need `pnpm fixtures`) and `pnpm build`; the CI entrypoint checks in the base image; `docker build -f docker/Dockerfile` (the deps stage's better-sqlite3 load check passes: N-API prebuild); the image healthy, `/api/v1/system/health` 200, first-user setup (argon2id from `node:crypto`) 200, and Settings → About reports node `26.13.1`.

## 2026-11-17 Titles and posters from sidecar files

- Sources, in order: for an episode, `<stem>.nfo` (episodedetails), then `tvshow.nfo` in the file's folder or its parent; for a movie, `<stem>.nfo`, then `movie.nfo` (not in the library root, where it would name every loose file). Posters: `<stem>-poster`, `poster`, `folder`, `cover` (`.jpg`, `.jpeg`, `.png`, `.webp`); episodes use `poster` or `folder` in the show folder. The file name is the fallback for the title.
- A `.nfo` is read only up to 1 MB, never through a symlink, and nothing outside the library is read. A bad sidecar is ignored and leaves the file-name result.
- Media info is stored on the job at queue time (`jobs.media`, migration 0019) and never refreshed. Older jobs show a file-name title and no poster. The catch-up scan reads sidecars only for new files.
- Thumbnails are 208 px JPEGs in `<config>/posters`, named by a hash of the poster path and built on first request. At most 2 are built at once, a failed build is not retried for 10 minutes, and a failed rebuild keeps serving the older thumbnail. A thumbnail takes its source's modification time and is rebuilt when the source's time differs (newer or older), so a source dated in the future is built once. They are never pruned.
- ffmpeg reads the image from stdin with a forced demuxer, so it never opens a library path, and decodes at most 40 megapixels (`-max_pixels`): a larger image gets no thumbnail.
- `GET /api/v1/jobs/:id/poster` is session-only, like the job log: API tokens get 403.
- Transcoda never writes into a library for this.
- Follow-up: looking up titles and artwork through the Sonarr, Radarr and Jellyfin plugins.

## 2026-11-20 Node states on the job trace

- **A badge on the job trace is the job's own warning or problem for that node.** The editor's badge says what is wrong with a node of the graph (its workflow issues); a job's graph is a pinned version that already ran, so those issues say nothing about the job. What a viewer of a job needs badged is the step that left something to look at although the job went on: a webhook that did not send, a plugin finish step that failed, a size gate or write step that failed after the first write. Those were job-wide strings (`result.warnings`, `result.problems`) with no node.
- **`result.nodeProblems`** (`{ workflowPath, nodeId, severity: 'problem' | 'warning', message }`, migration 0022, `job_results.node_problems_json`) ties each of those to its node, with the same text as in the warnings or problems. The walk tags every core finish action with its `nodeId` and `workflowPath` (plugin actions already carried them), and the pipeline records the entry where it adds the warning or problem. A required plugin step on a side branch (nothing written) is a `warning` there, as in the result. Results from before have `[]`: no badge. The Render's own warnings (a GPU encode that fell back to software or to CPU decoding, ignored leading decoder errors, a frame count that disagrees with the source's tag, verify's warnings) are told on the Render; Replace original's problems after the write (a recovery note, a sidecar that could not be recycled) on Replace original.
- **Drawn in the editor's badge language** (`withJobProblems`): the word ("problem" with the alert glyph, "warning" with "!") on an amber badge, amber for both because the job page lists a done job's problems in amber ("needs attention"). A trace problem never draws the edges into the node broken. The card's name says the word and the message, a line under its reason shows "Problem: …" or "Warning: …", the badge has the message as its tooltip, and the step list shows it as a note on the step.
- **The node at work when execute ends is recorded.** The pipeline keeps the node whose work is under way (`runningNode`): the Render while sidecars are copied, covers extracted, the file encoded and verified; then each finish step. When the job fails there (after the retry, never on a requeue), that node gets a `failed: <reason>` trace entry, as a walk failure does, so it reads failed and the steps after it "didn't run". A cancel writes `canceled: the job was canceled during this step` instead: a new trace state `cancelled` (word "canceled", a dashed neutral ring, a neutral "Canceled" step badge), matching the job's own neutral canceled chip rather than reading as a failure.
- **The lit node is the node at work.** The trace used to light Encode video while ffmpeg ran, so a failure traced on the Render landed on a node that was never lit. The Render is what runs ffmpeg (its entry says "encoded and verified"), so the light moved, not the failure: the engine reports `runningNode` as the job's current node (the Render while encoding and verifying, each finish step after it, Replace original while replacing), and the job page and the activity widget light it (`executingNode`; before a report, the Render on the walk, or Replace original while replacing). A walk without a Render still lights the encoding node, and a failure or cancel is traced on it. Validation no longer queues such a walk, so this is a fallback. The steps on a side branch where nothing writes (a size gate's No, Render's Damaged) are each the current node while they run.
- **A server restart mid-encode.** The startup sweep requeues a running job once; the rerun walks again and writes fresh entries, so nothing is added then. When the sweep fails the job instead (its second interruption) while it was encoding or verifying, it writes `failed: interrupted, the server stopped during this step` on the Render of the job's walk (from the pinned version's graph). Jobs interrupted while deciding or building get nothing: the engine does not persist which node it was at. A Render that already has its own finish entry in that attempt (Done or Damaged) gets none: the stop came in a step behind it, such as a size gate's No branch, which keeps the job in verifying.

## 2026-11-20 Design audit fixes

- Focus is never hidden under the sticky top bar: `html` has `scroll-padding-top` of the top bar's height plus 16px. The editor has no top bar and does not scroll the page, so it gets none. The sticky side nav starts below the bar, so it needs none either.
- The editor has an h1 (the workflow's name, visually hidden): the breadcrumb already shows the name, as the rename button.
- A note's `# heading` on the canvas is a bold lead-in (`p.markdown-heading`), not an `<h4>`. The canvas is not part of the page outline, and the h4 skipped levels on the job page (h2 to h4) and in the editor (h1 to h4).
- React Flow's focusable wrapper of each card, group and values card has an `aria-label` (the card's title, the group's name, "Values"), at every zoom level. The icon-only tile shows no words, so the wrapper had no name.
- The Jobs stat tiles' accessible names start with the visible label ("Queued: 37, show these jobs", not "Show Queued: 37"), as WCAG 2.5.3 asks.
- The job and run pages' breadcrumbs end in the current item (the job's title, the run's workflow and version) with `aria-current="page"`, using the libraries' `Crumbs` and its `›` separator, instead of a dangling "Jobs /".
- Target size (WCAG 2.5.8, 24px at least). Small text links outside a sentence (job facts, workflow names, the libraries' Feeds links, the recycle page's Settings link) get `.text-target`: 4px of padding above and below, cancelled by a negative margin, so the text does not move. The library name gets the same 4px. `wf-activate` is a 32px target that still takes 24px of the line. The Jobs table's titles needed nothing: their `::after` already covers the row.
- The canvas's "+" and group toggle are 44 canvas px, so they fell to 18px on screen at 0.4 zoom. Their size is now `max(44px, 24px / zoom)`. A small `ZoomVar` component writes the zoom to `--tc-zoom` on the React Flow wrapper.
- `.btn-sm::before` did not reach 44px on a bordered button: an absolute pseudo-element is placed against the padding box, so `inset: -4px 0` gave a ghost or secondary button 42px. It is now a 44px-tall box centred on the button. The editor header's 40px buttons had the same gap and got the same fix.
- The editor canvas and the job page's trace open at a readable zoom, not a fit-all of about 0.41 (titles at 5 to 6px). The floor is 0.75 (`READABLE_ZOOM`): it is where the full card comes back (N9), and the 15px title lands at about 11px, the smallest size the UI sets text in. A graph that fits whole at 0.75 or more still opens whole.
- A graph too wide for the floor opens at 0.75 with the trigger (a sub-workflow's start, else the leftmost card) 48px from the left edge, so the flow reads on to the right. The editor centres the graph vertically when it fits, else the trigger. The trace already started from its left edge past its floor; only the floor moved (from 0.2). "Fit view" in the controls still shows the whole graph.
- On a phone the trace keeps fitting the whole graph down to 0.1: a drag there scrolls the page, so a cut-off graph could not be panned into view.
- The editor's first view is `openViewport` (a pure function, tested) run by a small `OpenView` component before paint, in place of React Flow's `fitView` prop. A remembered viewport still wins.
- tokens.css differs from the handoff: a new `--line-control` token (#7A766F dark, #837F76 light) for form control edges. The handoff drew them in `--line-strong`, about 1.3:1 on `--raised`. The new edge is 3.4:1 (dark) and 3.3:1 (light) on `--raised`, and higher on the other surfaces (WCAG 1.4.11). Inputs, the listbox field button, segmented controls, chip fields, toggle chips and the on-card inputs use it. Native checkboxes and radios keep the browser's own edge.
- tokens.css differs from the handoff: motion tokens `--ease-out` (cubic-bezier(0.23, 1, 0.32, 1)), `--dur-fast` (120ms) and `--dur-base` (160ms). Every UI transition uses them. Progress fills and loops keep their own linear timing.
- tokens.css differs from the handoff: reduced motion clamps every animation and transition to 0.01ms and one run, instead of `animation: none`. Things that need an end state still reach it. The loops (path dash, running border) are still switched off in styles.css, and the spinners only turn when motion is allowed.
- A button moves down 1px while pressed, only when motion is allowed. The transform is on the button, not on its `::before` hit area, which has its own centring transform.
- Hover fills, colours and underlines apply only under `@media (hover: hover)`, so a tap does not leave them stuck. Focus styles are not gated. Overrides that undo a library's hover (the canvas controls' disabled state, `a.btn`) and the info tip's reveal stay ungated.
- The current nav item is a neutral `--raised` row with `--text` and the icon in `--accent-text`, not a lime fill: it weighed as much as the page's primary button. The settings sub-nav already looked like this; both now keep the normal weight.
- The viewed row in the versions panel is a `--line` fill, not an inset side tab. The panel itself is `--raised`, so the fill is one step up. A selected edge on the canvas is 2px heavier, not a drop-shadow glow.
- The danger outline button's text is 14px, like the other small buttons. h1 and h2 have line-height 1.2 (they inherited the body's 1.4); the job result heading went from 1.3 to 1.2.
- Type scale: every `font-size` in styles.css is a `--fs-*` variable. tokens.css has display, h1, h2, body, small and mono; four more sit at the top of styles.css because tokens.css is vendored: `--fs-micro` 11px, `--fs-ui` 14px, `--fs-h3` 17px and `--fs-title` 32px. Raw sizes moved by at most one step: 10px went up to 11px, 16px and 18px became 17px, and the odd display sizes (22, 24, 26, 28, 30, 34) went onto h2 (20), h1 (28) or title (32). The Jobs stat figure (24px to 20px), the plan percentage (30px to 32px) and the credentials title (34px to 32px) are the visible changes. A test fails when a raw px size comes back.

## 2026-11-23 Code consistency checks

Rules the code already followed almost everywhere are now checked, so they stay that way. All are errors; the Biome ones live in one `overrides` block and one `plugins` list in `biome.json`.

- Relative imports name the file's extension (`./x.ts`). Nine web imports had none (`useImportExtensions`).
- No default exports. Exempt: tool config files (`*.config.ts`), plugin fixtures (the plugin format is a default export) and vitest's `globalSetup` (`noDefaultExport`).
- No `console` in app and package source. The server logs through `logger.ts`, the one exempt file; the web app's event bus has a reasoned suppression, since it has no logger (`noConsole`).
- No floating promises and no `await` on a value that is not a promise. There were none of the first and two of the second (`noFloatingPromises`, `useAwaitThenable`; both nursery rules, pinned by the exact Biome version).
- No import cycles (`noImportCycles`). There were none.
- `T[]`, not `Array<T>` (`useConsistentArrayType`). 41 were changed; `[]` was the common form.
- Tests use `it`, keep hooks above the tests, and are never committed with `.only` or `.skip`. `skipIf` stays allowed (`useConsistentTestIt`, `useTestHooksOnTop`, `noFocusedTests`, `noSkippedTests`).
- No `any` and no non-null `!`: these were warnings and are now errors. One `!` was left, in a test.
- No deprecated imports (`noDeprecatedImports`): React 19's `FormEvent` became `SubmitEvent` in seven submit handlers.
- Server, package and script file names are kebab-case. Migrations keep `NNNN_snake_case.ts`. Web file names are mixed (PascalCase components, camelCase and kebab-case modules), so they are not checked yet (`useFilenamingConvention`).
- Custom GritQL rule `scripts/biome/utc-dates.grit`: no local-time `Date` methods (`getHours`, `toLocaleDateString`, ...) in server or package code, because times are UTC. The two places that mean local time (backup file names, the day in an "already processed" reason) have a `biome-ignore lint/plugin/utc-dates` with the reason.

  - `toLocaleString` also exists on numbers. It is flagged only on `new Date(...)`, or on a receiver whose name reads as a date: `d`, or a name containing `Date`, `Time`, `Now`, `When` or `Day`, or ending in `At`.

- Guard test `apps/server/src/db/migration-conventions.test.ts`: migration files are named `NNNN_snake_case.ts` and numbered 1..N without gaps. Each one is registered in `migrations/index.ts` in order, with a matching `version` and `name`, and has its own test. 1–4 and 12 have no test and are allowlisted there; the list may only shrink.

## 2026-11-26 ffmpeg 8 timestamps: verify's decode and progress (#154, #155)

The first nightly ran the real-ffmpeg tests against jellyfin-ffmpeg 8.1.3, the version the image ships; until then they ran on ffmpeg 9 only. Two differences showed.

- **Decoding to the null muxer (#155).** ffmpeg 8 moves decoded video frames to the frame rate's time base (1/24) on their way to the null muxer. With Matroska's millisecond timestamps and B-frames, two frames round onto one, and the muxer logs "non monotonically increasing dts … 2 >= 2" at error level. That is about ffmpeg's own discarded output, not the file, but verify and the source check take error lines as damage: an MKV copy of an ordinary B-frame video failed verify.
  - Fix: `-enc_time_base:v demux` (`NULL_TIMESTAMPS` in `decoder-names.ts`) on every null decode: verify's decodes, and the source check's read and locating pass.
  - Video only. With audio in milliseconds, a frame a seek trims (decode-end from 0.021 s) and the next one round to the same timestamp the same way.
  - A truncated file is still caught; ffmpeg 9 accepts the option and never logged the lines.
- **Progress with a copied image track (#154).** ffmpeg 8 reports `out_time` as the earliest stream's last dts, and `N/A` while any unfinished stream has none (`trailing_dts` in `ffmpeg_sched.c`). A copied image track has one packet, which in Matroska carries no dts, so `out_time` is `N/A` for the whole encode. From an MP4 the packet has a dts and `out_time` stays at about 0. ffmpeg 9 reports the furthest stream instead.
  - Before, a block without an out time was dropped. Such an encode sent no progress (no percent, no ETA), and the stall guard got no sample at all, so after `TRANSCODA_ENCODE_STALL_MINUTES` (60) it would have stopped a healthy long encode as "wrote no output". The frame-count check also read a stale block.
  - Now every complete block is a sample, with `outTimeSeconds` null for `N/A`.
    - The stall guard counts size growth as before; an encode that never starts still sends no block at all, in both versions, so "no output" keeps its meaning.
    - The job's progress takes the further of the out time and `frame=` over the first video stream's frame rate (`withFrameTime`).
    - A source decoder error is placed at that same furthest position, which the confirming decode reads around. With no position known (no out time and no frame rate), it is ignored with a warning rather than placed at 0, where the confirming decode would read the wrong part of the source.
  - ffmpeg 8 also holds a copied image track's packets for up to 10 s of media (`-max_interleave_delta`) before writing. The real-ffmpeg test of the image track therefore checks that the copied run's progress starts within the limit, not that it grows.
